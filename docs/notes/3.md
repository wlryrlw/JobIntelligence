## 1. 阶段任务、作用和为什么需要它

### 1.1 阶段三要解决什么问题

阶段零到阶段二已经建立了项目基础设施、招聘数据采集、ETL、数据质量检查、查询编排和市场统计能力。系统能够回答：

- 某城市有哪些职位？
- 某类岗位中哪些技能出现得多？
- 某些职位的薪资分布如何？
- 某家公司或某个关键词对应多少职位？

但“市场上需要什么”不等于“求职者是否适合”。用户还需要知道：

- 我的简历覆盖了哪些目标岗位技能？
- 简历中哪些技能有项目证据，哪些只有关键词？
- 某项技能是必须要求还是优先项？
- 哪些项目应该放到简历前面？
- 面试前应该准备哪些主题？
- 这些结论是依据简历哪一段、职位哪一段或哪项统计得到的？

阶段三把个人材料和市场数据接起来：

    简历文件
      ↓
    解析、大小限制、页数限制、文本校验
      ↓
    PII 脱敏和结构化证据抽取
      ↓
    ResumeEvidence
                    + 目标岗位筛选条件
                    ↓
              已发布职位数据
                    ↓
                JobProfile
                    ↓
                CareerAgent
                    ↓
              CareerReport

本阶段的核心产物不是一个没有解释的匹配分数，而是一份带证据、可追溯、可执行的职业分析报告。

### 1.2 设计文档中阶段三的主要任务

阶段三的最小闭环包括：

1. 支持上传 TXT、Markdown、PDF 简历。
2. 限制文件字节数、PDF 页数和最小文本长度。
3. 在进入模型和分析流程前脱敏常见个人隐私信息。
4. 抽取简历中的技能、项目行、量化结果等结构化证据。
5. 根据关键词、城市、公司、经验、学历等条件筛选职位。
6. 从有效职位描述中构建 JobProfile。
7. 统计技能出现次数、出现率、要求类型、薪资分布、经验分布和学历分布。
8. 对比 ResumeEvidence 和 JobProfile，生成 covered、partial、missing 三类覆盖度。
9. 输出结构化 CareerReport。
10. 缺少目标岗位或简历标识时请求补充，而不是猜测。
11. 数据集、简历、解析器或模型失败时显式报告错误。
12. 默认不依赖外部实时抓取和 LLM，先保证确定性基线可用。
13. 用测试覆盖正常流程、边界条件、隐私和所有权隔离。

MVP 明确不包含 OCR、DOCX、自动投递、复杂推荐排序、长期记忆和无人工确认的整份简历改写。这是范围控制，不是遗漏：先建立可审计的证据链，再根据评估结果扩展。

### 1.3 为什么不能只做一个大模型提示词

直接把简历和 JD 全文发给模型，再让模型回答“是否匹配”，有几个问题：

- 模型可能编造简历中不存在的技能、规模、指标和职责。
- Python、Python3、K8s、Kubernetes 等别名可能造成不稳定匹配。
- 用户看不到结论对应的原始证据。
- 邮箱、手机号、地址等隐私会扩大传播范围。
- 技能出现率、薪资单位和统计分母可能被模型误读。
- LLM 不可用时整个功能不可用。
- 自然语言输出无法作为稳定的前端和下游接口。

因此阶段三采用：

    确定性输入校验
      + 本地 PII 脱敏
      + canonical skill 归一化
      + 结构化统计
      + 严格 Pydantic 校验
      + 可选的 LLM 增强

LLM 只能参与被明确授权的技能抽取或建议组织，不能替代权限校验、统计公式和事实验证。

### 1.4 验收标准

| 场景 | 期望行为 |
| --- | --- |
| 上传 TXT/Markdown | 成功解析并生成 resume_id |
| 上传 PDF | 在页数和文本限制内成功提取文本 |
| 文件超过上限 | 读取过程中拒绝并返回 413 |
| 扫描型 PDF | 文本提取为空时明确失败，不假装成功 |
| 简历含邮箱、电话 | 分析 evidence 不保留这些常见直接标识符 |
| 缺少 target 或 resume_id | 返回 clarify，不自动猜测 |
| resume_id 属于其他用户 | 不泄露资源所有权信息 |
| 数据集不可用 | 返回 request_crawl 或 failed |
| LLM 关闭 | 正则和确定性分析仍可运行 |
| LLM 输出非法 | 严格拒绝或在允许的位置回退 |
| 样本量很小 | 增加 warning，降低结论强度 |

## 2. 总体架构和调用链

### 2.1 Career 子包的职责

新增的 career 包大致分为以下模块：

    backend/app/career/
    ├── models.py     阶段三内部中间模型
    ├── resume.py     简历解析、脱敏、证据抽取
    ├── skills.py     技能目录、别名、正则和 LLM 抽取
    ├── profile.py    从职位数据构建目标岗位画像
    ├── agent.py      生成覆盖度分析和职业报告
    └── store.py      简历内容、元数据和 evidence 存储

外部边界包括：

- POST /api/resumes：读取上传文件、解析并保存。
- DELETE /api/resumes/{resume_id}：当前用户删除自己的简历。
- QueryWorkflow：连接查询参数、数据集、简历、画像和 Agent。
- contracts.py：作为跨层数据契约。
- config.py：提供 storage path、上传限制和 career_llm_enabled。

### 2.2 上传链路

    用户上传
      ↓
    API 分块读取，超过 max_bytes 立即拒绝
      ↓
    parse_resume 校验后缀、大小、页数、文本长度
      ↓
    redact_pii 在本地替换邮箱、电话等字段
      ↓
    extract_resume_evidence 提取技能、项目和量化结果
      ↓
    ResumeStore 保存 source、metadata、evidence
      ↓
    返回 resume_id 和简短元数据

原始内容、脱敏内容和结构化 evidence 必须分层：

- source：为了用户删除、重新解析或审计而保留的本地原文件。
- redacted_text：解析过程中的脱敏文本，不应进入普通日志。
- evidence：下游分析真正需要的最小事实集合。
- API 返回：返回标识和状态，不返回完整原始简历。

### 2.3 分析链路

    用户问题
      ↓
    QueryPreprocessor 提取 target、city、resume_id 等参数
      ↓
    Coordinator 判断缺少参数、数据集状态和用户权限
      ↓
    ResumeStore 按 owner_id 加载证据
      ↓
    JobProfileBuilder 读取 ETL published 数据
      ↓
    CareerAgent 进行覆盖度分析
      ↓
    QueryResult.career_report 返回结构化报告

职责划分是：

- Coordinator/Workflow：资源门控、状态流转、权限和错误归一化。
- ResumeStore：文件和证据存取、所有权隔离。
- JobProfileBuilder：市场数据筛选和统计。
- CareerAgent：已准备证据之间的职业分析。
- API：HTTP 输入输出边界。
- Pydantic contracts：跨层稳定接口。

CareerAgent 不应该自己读任意路径、自己判断用户所有权或自己抓取招聘网站。这样可以防止业务分析层变成同时处理权限、存储、网络和提示词的“上帝函数”。

## 3. 核心数据契约

### 3.1 EvidenceRef

contracts.py 中的 EvidenceRef 用来表示一条可以被复核的证据：

    class EvidenceRef(BaseModel):
        source: Literal["resume", "job_description", "market_data"]
        quote: str
        location: str | None = None
        confidence: float = Field(ge=0.0, le=1.0)

参数说明：

- source：证据来自简历、职位描述还是市场数据。
- quote：用于支撑结论的短文本，而不是整份文档。
- location：页码、行号、职位 ID 或字段路径。
- confidence：抽取器的置信度，限制在 0 到 1。

证据引用强迫系统把“结论”和“依据”分开。例如：

    结论：目标岗位普遍需要 Python。
    依据：筛选后的 100 条有效 JD 中有 73 条包含 Python。

如果只保存“Python 很重要”，用户和测试都无法判断这个判断是否有依据。

### 3.2 SkillMention

    class SkillMention(BaseModel):
        model_config = ConfigDict(extra="forbid")

        skill: str
        display: str
        category: str
        requirement: Literal["must_have", "preferred", "unknown"]
        evidence: EvidenceRef
        confidence: float = Field(ge=0.0, le=1.0)
        source: Literal["resume", "job_description"]
        extractor_version: str

字段设计：

- skill：归一化后的 canonical key，例如 python、kubernetes。
- display：面向用户展示的名称，例如 Python、Kubernetes。
- category：语言、框架、数据库、云平台等类别。
- requirement：must_have、preferred 或 unknown。
- evidence：原文短证据及位置。
- source：简历或职位描述。
- extractor_version：规则、目录或模型版本。

extra="forbid" 的意义是：如果外部模型返回了系统不认识的字段，Pydantic 会拒绝，而不是把未知字段悄悄带入核心流程。

### 3.3 ResumeEvidence

    class ResumeProjectEvidence(BaseModel):
        title: str
        evidence: list[EvidenceRef]

    class ResumeEvidence(BaseModel):
        skills: list[SkillMention]
        projects: list[ResumeProjectEvidence]
        quantitative_results: list[EvidenceRef]
        source_hash: str
        extractor_version: str

ResumeEvidence 只保存分析需要的脱敏事实：

- skills：简历里可定位的技能提及。
- projects：项目标题和项目证据。
- quantitative_results：延迟下降、处理量、错误率等量化证据。
- source_hash：原始来源的 hash，用于识别版本和审计。
- extractor_version：本次证据抽取器版本。

它不把完整简历全文复制到每一个下游对象中，可以减少隐私传播和日志污染。

### 3.4 JobProfile

    class JobProfileSkill(BaseModel):
        skill: str
        display: str
        category: str
        occurrence_count: int
        occurrence_rate: float
        requirement: Literal["must_have", "preferred", "unknown"]
        evidence: list[EvidenceRef]
        extractor_version: str

    class JobProfile(BaseModel):
        target: str
        filters: dict[str, str]
        valid_jd_count: int
        skills: list[JobProfileSkill]
        salary: dict[str, float | None]
        experience_distribution: dict[str, int]
        degree_distribution: dict[str, int]
        warnings: list[str]
        extractor_version: str

技能出现率的分母必须定义清楚：

    occurrence_rate =
        包含该技能的有效 JD 数量 / 有效 JD 总数量

例如，100 条有效 JD 中 73 条包含 Python，则 Python 的出现率是 0.73。不能把词语总出现次数作为分母，也不能把没有可用 JD 文本的职位算入分母。

### 3.5 SkillCoverageItem 和 CareerReport

    class SkillCoverageItem(BaseModel):
        skill: str
        display: str
        category: str
        status: Literal["covered", "partial", "missing"]
        requirement: Literal["must_have", "preferred", "unknown"]
        jd_evidence: list[EvidenceRef]
        resume_evidence: list[EvidenceRef]
        suggestion: str
        confidence: float
        extractor_version: str
        jd_occurrence_rate: float

三种状态的语义：

- covered：简历中有归一化后的技能，并且有相关简历证据。
- partial：简历出现相关技能或项目线索，但深度、上下文或结果证据不足。
- missing：当前简历证据里找不到该技能或相关项目证据。
- missing 不等于求职者绝对不会，只表示当前材料没有可验证证据。

CareerReport 还包括：

- report_id、title、summary。
- resume_id、target。
- job_profile。
- facts：市场和简历直接支持的事实。
- recommendations：基于事实的行动建议。
- skill_coverage：逐项覆盖度。
- rewrite_directions：项目改写方向。
- interview_checklist：面试准备清单。
- generated_at：生成时间。

结构化报告方便前端渲染、测试断言、保存版本和后续离线评估。

## 4. 简历解析、脱敏和证据抽取

### 4.1 parse_resume 的职责和参数

resume.py 的主要入口可以概括为：

    def parse_resume(
        filename: str,
        content: bytes,
        limits: ResumeLimits | None = None,
    ) -> ParsedResume:
        ...

ResumeLimits 当前包含：

- max_bytes：默认 5 MB。
- max_pages：默认 10 页。
- min_text_chars：默认至少 10 个有效字符。

ParsedResume 至少包含：

- filename：原始文件名。
- media_type：根据后缀或内容确定的媒体类型。
- size：原始字节数。
- page_count：PDF 页数，文本文件按 1 处理。
- text：解析后的文本。
- redacted_text：脱敏文本。
- redaction_count：替换次数。
- source_hash：来源内容 hash。

解析过程：

1. 根据后缀支持 txt、text、md、markdown 和 pdf。
2. 解析前检查字节数。
3. 文本文件使用 UTF-8 解码，解码失败抛出 ResumeParseError。
4. PDF 使用 pypdf 逐页读取。
5. 超过页数上限直接失败。
6. 清理空白后检查最小文本长度。
7. 执行本地 PII 脱敏。
8. 计算来源 hash。

这体现了“先限制资源，再解析”的原则。不能先无条件读入一个未知大小文件，再在最后检查限制。

### 4.2 上传 API 的有界读取

routes.py 中的上传读取逻辑使用分块和累计字节数：

    async def _read_upload(
        upload: UploadFile,
        max_bytes: int,
    ) -> bytes:
        chunks: list[bytes] = []
        total = 0

        while True:
            chunk = await upload.read(1024 * 1024)
            if not chunk:
                break

            total += len(chunk)
            if total > max_bytes:
                raise HTTPException(
                    status_code=413,
                    detail="resume file is too large",
                )

            chunks.append(chunk)

        return b"".join(chunks)

参数解释：

- upload：FastAPI 的异步上传对象。
- max_bytes：允许的最大字节数。
- 1024 * 1024：每次读取 1 MiB。
- total：累计读取的字节数。
- 超限后立即抛出 413，而不是继续读完整文件。
- 合法文件在当前 5 MB 上限内拼成 bytes，交给 parse_resume。

如果未来允许更大文件，应改成临时文件加流式 hash，避免把完整文件保存在内存中。

### 4.3 PII 脱敏

redact_pii 是本地确定性函数，目前主要处理：

- 邮箱。
- 手机号。
- 固话。
- 身份证号。
- 带“姓名”“地址”等标签的字段。

例如原文：

    姓名：张三
    邮箱：zhangsan@example.com
    手机：13812345678
    项目：使用 Python 和 FastAPI 构建招聘系统，延迟降低 40%。

分析侧应接近：

    姓名：[REDACTED_NAME]
    邮箱：[REDACTED_EMAIL]
    手机：[REDACTED_PHONE]
    项目：使用 Python 和 FastAPI 构建招聘系统，延迟降低 40%。

设计原则：

1. 在 LLM 调用和 evidence 抽取前执行。
2. 保存 redaction_count，便于测试和审计。
3. 原始 source 与脱敏 evidence 分开存储。
4. 脱敏失败不能静默假装完成。

当前边界也必须说明：

- 未标注的姓名、地址和社交账号不保证全部识别。
- 图片里的隐私不在纯文本正则覆盖范围内。
- 扫描 PDF 没有 OCR，因此不会自动提取图片文字。
- 脱敏规则需要结合真实样本继续扩展。

### 4.4 简历证据抽取

extract_resume_evidence 的目标不是重述简历，而是保留可支撑报告的最小证据：

- 技能提及。
- 项目标题和项目行。
- 量化结果。
- 原文位置和来源。

简化代码：

    def extract_resume_evidence(
        parsed: ParsedResume,
        catalog: SkillCatalog,
    ) -> ResumeEvidence:
        skills = catalog.extract_resume(parsed.redacted_text)
        projects = extract_project_lines(parsed.redacted_text)
        results = extract_quantitative_results(parsed.redacted_text)

        return ResumeEvidence(
            skills=skills,
            projects=projects,
            quantitative_results=results,
            source_hash=parsed.source_hash,
            extractor_version=RESUME_EXTRACTOR_VERSION,
        )

只保存短 evidence 的原因：

- 报告需要的是支撑判断的片段，不是全文复制。
- 短文本更容易展示和人工复核。
- 可以减少日志和数据库中的敏感内容。
- 将来可把 raw source 放入加密存储，而分析模块只接触 evidence。

### 4.5 ResumeStore 的目录和权限

当前本地存储可以抽象为：

    resumes/
    └── owner_id/
        └── resume_id/
            ├── source.bin
            ├── metadata.json
            └── evidence.json

metadata.json 保存文件名、大小、页数、媒体类型和 hash；evidence.json 保存脱敏结构化证据；source.bin 是原始文件。

load 和 delete 必须同时接收 owner_id。只按 resume_id 访问会产生越权风险。

存储层还要：

- 限制 resume_id 格式。
- 拒绝路径分隔符、点号路径和异常字符。
- 用 resolve 后确认最终路径仍位于 owner 目录。
- 删除前只定位已经校验的具体目录。
- 不把用户输入直接当成任意文件路径。

## 5. 技能抽取和归一化

### 5.1 SkillCatalog 为什么重要

SkillCatalog 的主要作用是把表面不同的技能名称归为一个 canonical key：

    k8s、K8S、Kubernetes → kubernetes
    Python、Python3、Python 3 → python

如果不归一化，简历写 K8s、职位写 Kubernetes 时会被错误判定为 missing；统计时同一技能也会被拆成多个词。

技能字段应同时保留：

- canonical key：用于比较、统计和覆盖判断。
- display：用于用户展示。
- category：用于分类分析。
- evidence：用于复核。
- extractor_version：用于结果版本化。

### 5.2 正则基线

阶段三默认使用 SkillCatalog 的确定性正则基线：

- 从 ETL 阶段的 alias 表加载技能。
- 使用安全边界匹配，避免把一个词误判成另一个词。
- 记录出现文本、位置、source 和 confidence。
- 根据技能附近的局部上下文判断 requirement。

使用正则的优点：

- 可离线运行。
- 结果稳定。
- 便于单元测试和回归。
- 不产生模型费用。
- 失败时容易解释。

缺点是无法很好理解复杂否定句、隐含能力、跨段落上下文和同义表达。因此它是 MVP 基线，不是最终 NLP 能力。

### 5.3 must_have、preferred 和 unknown

职位描述中的技能要求类型不能全部硬编码成 must_have。可以查看技能附近的局部条款：

- “必须、要求、掌握”等词，倾向于 must_have。
- “优先、加分、熟悉即可、了解即可”等词，倾向于 preferred。
- 没有足够上下文时返回 unknown。

unknown 是有价值的状态：它表示证据不足，而不是系统强行猜测。

### 5.4 可选 LLM 抽取和二次验证

当配置 career_llm_enabled 打开时，可以调用 ModelClient.chat_json，让模型抽取 JD 技能。模型输出仍然必须严格验证：

    class LlmSkillItem(BaseModel):
        model_config = ConfigDict(extra="forbid")

        skill: str
        display: str
        category: str
        requirement: Literal["must_have", "preferred", "unknown"]
        evidence: str
        confidence: float = Field(ge=0.0, le=1.0)

    class LlmSkillResponse(BaseModel):
        model_config = ConfigDict(extra="forbid")

        skills: list[LlmSkillItem]

验证步骤：

1. 解析模型返回的 JSON。
2. 用 Pydantic 校验字段、枚举和数值范围。
3. evidence 必须是原始 JD 的真实子串。
4. skill 必须能被本地 SkillCatalog 归一化。
5. 合并同一 canonical skill 的重复项。
6. 保存 extractor_version。
7. 对不合法输出显式失败或按调用策略回退。

最重要的防护是“evidence 原文验证”：模型说 JD 有某项技能，不等于 JD 真的写了这项技能。

### 5.5 LLM 失败策略

默认策略：

1. LLM 关闭时使用正则。
2. LLM 开启时先严格校验。
3. 可选增强位置可以回退到正则并记录 warning。
4. 用户要求完整高精度结果时，也可以直接返回 failed。
5. 禁止吞掉异常后生成看似完整但没有证据的报告。

## 6. JobProfile：构建目标岗位画像

### 6.1 数据来源和筛选

JobProfileBuilder 读取 ETL 的发布目录，主要使用：

- jobs.csv：职位主表。
- job_details.csv：职位描述、薪资、经验和学历。
- _schema.json：数据 schema 和版本信息。

筛选条件包括：

- target 关键词。
- 城市。
- 公司。
- 经验。
- 学历。

阶段三读取已经发布的数据，不让 CareerAgent 直接访问招聘网站，因此可以复用阶段一的快照、字段归一化和数据质量处理。

构造参数：

    JobProfileBuilder(
        database_root: Path | None = None,
        *,
        model_client: ModelClient | None = None,
        use_llm: bool = False,
    )

参数含义：

- database_root：数据发布根目录，缺省时使用项目默认根目录。
- model_client：可选模型客户端。
- use_llm：是否启用 LLM 技能抽取，默认 false。

### 6.2 有效 JD 和出现率公式

先排除没有可用文本、格式不正确或无法关联详情的职位，得到 valid_jd_count。

    occurrence_count(skill) =
        筛选后且有效 JD 中包含 skill 的 JD 数量

    occurrence_rate(skill) =
        occurrence_count(skill) / valid_jd_count

示例：

- 筛选后得到 120 条职位。
- 其中只有 100 条有有效职位描述。
- 73 条有效 JD 包含 Python。
- Python occurrence_count 为 73。
- Python occurrence_rate 为 0.73。

不能把所有原始职位数量当分母，因为没有 JD 文本的职位无法参与“是否包含技能”的判断。

### 6.3 薪资、经验、学历和 warning

薪资首先统一到相同单位。若职位给出区间，则可使用中点：

    salary_midpoint = (annual_min + annual_max) / 2

再对有效样本计算 p25、p50、p75。百分位数使用线性插值，避免简单取整位置造成不连续。

JobProfile 应明确保存：

- 薪资单位。
- p25、p50、p75。
- 参与统计的样本量。
- 经验分布。
- 学历分布。
- 低样本 warning。

当有效 JD 少于 10 条时添加 small sample warning。这个阈值是工程上的风险提示，不是统计学上的完整置信区间。

应该分开保存：

    facts:
      “在 100 条有效 JD 中，Python 出现于 73 条。”

    recommendations:
      “建议把一个有真实性能指标的 Python 项目放到简历靠前位置。”

facts 可由统计直接验证；recommendations 是基于 facts 的行动建议，不应伪装成市场事实。

## 7. CareerAgent：覆盖度和报告

### 7.1 输入输出边界

CareerAgent 的主要入口可以概括为：

    CareerAgent.analyze(
        resume: ResumeEvidence,
        profile: JobProfile,
        resume_id: str,
        target: str,
    ) -> CareerReport

它不负责：

- 接收上传文件。
- 读取任意路径。
- 判断当前用户是否拥有简历。
- 实时抓取招聘网站。
- 在没有证据时创造简历事实。

它只接收已经通过边界校验的 ResumeEvidence 和 JobProfile，再返回 CareerReport。

### 7.2 覆盖算法

简化逻辑：

    对 JobProfile.skills 中每一项技能：
        在 ResumeEvidence.skills 中按 canonical skill 查找
        如果找到技能并且存在相关简历证据：
            status = covered
        如果找到技能但证据不足，或项目可能相关：
            status = partial
        否则：
            status = missing

    根据 requirement、occurrence_rate 和证据生成 suggestion

示例：

- 简历写“使用 Python 和 FastAPI 完成接口开发”，目标要求 Python：可能 covered。
- 简历技能列表写 Kubernetes，但没有项目或职责：可能 partial。
- 简历中完全没有 Kubernetes 或相关项目证据：missing。

partial 不能被忽略。它区分了“只出现关键词”和“有充分实践证据”。

### 7.3 为什么不用一个总匹配分数

MVP 不把所有因素压成 0 到 100 的分数：

- 技能重要性未必等于出现率。
- 必备技能和优先技能的权重需要人工标注和离线评估。
- 分数容易制造虚假的精确感。
- 用户更需要知道哪项技能缺证据以及下一步怎么补。
- 评分权重、阈值和缺失惩罚尚未经过真实数据验证。

更可解释的输出是：

- 每项技能的状态。
- 职位出现率。
- JD 证据。
- 简历证据。
- 建议和面试准备项。

将来如果引入评分，也应保留这些底层证据。

### 7.4 防止虚构简历事实

合法建议：

    当前证据只表明使用了 Python 和 FastAPI。
    建议补充真实请求量、延迟、错误率、部署方式和本人职责。

不合法的生成：

    使用 FastAPI 将系统吞吐量提升了 300%，服务了百万级用户。

除非原始简历明确包含这些数字，否则后一句是幻觉。

CareerAgent 可以要求用户补充真实指标，但不能替用户填写未经确认的数字；可以建议说明实验环境，但不能把实验项目写成生产上线。

### 7.5 可选 LLM 的合理位置

可选 LLM 适合：

- 把已经确认的事实组织成更自然的建议。
- 生成项目改写方向。
- 整理面试清单。

它不应替代：

- 权限判断。
- canonical skill 归一化。
- occurrence_rate 计算。
- JD 证据验证。
- covered、partial、missing 的底层判定。
- “是否拥有某事实”的最终决定。

这样 LLM 关闭时主流程仍然可用，开启时主要提升表达和辅助抽取，而不是改变事实底座。

## 8. Workflow、API 和状态处理

### 8.1 查询流程

QueryWorkflow 的职业路径大致是：

    1. 预处理用户问题，提取 target、city、resume_id。
    2. Coordinator 检查必要参数。
    3. 缺少 target 或 resume_id 时返回 clarify。
    4. 数据集不可用或过期时返回 request_crawl。
    5. ResumeStore 按 owner_id 加载简历。
    6. JobProfileBuilder 构建画像。
    7. CareerAgent 生成报告。
    8. 通过 QueryResult.career_report 返回。
    9. execution_log 记录资源门控和完成状态。

日志可以记录：

    resource_gate: passed
    career.resume_loaded: passed
    career.profile_built: valid_jd_count=100
    career.completed: covered=5, partial=2, missing=3

日志不应包含原始简历全文、邮箱、手机号或完整职位描述。

### 8.2 为什么缺参数时必须 clarify

如果用户只说“分析我的简历”，系统缺少：

- 哪个 resume_id。
- 目标岗位是什么。
- 可选的城市、公司、经验和学历条件。

系统不能猜最近一次上传，也不能自选目标岗位。正确行为是返回结构化澄清请求，例如：

    请补充：
    1. 要分析的简历 ID。
    2. 目标岗位关键词，例如 Python 后端或 AI Agent。
    3. 可选城市、公司、经验和学历过滤条件。

这可以避免错误目标、越权访问和看似完整但实际无效的报告。

### 8.3 资源所有权

对于不存在或不属于当前用户的 resume_id，外部接口不应暴露明显不同的错误语义。否则攻击者可以根据“资源不存在”和“资源属于别人”的差异推断其他用户是否上传了某份简历。

内部可以记录详细原因，外部只返回当前用户可理解且不泄露信息的结果。

## 9. 隐私、安全和错误处理

### 9.1 当前已经实现的保护

- 有界上传读取。
- 文件大小、页数和最小文本限制。
- 本地 PII 脱敏。
- raw source、metadata、evidence 分层保存。
- load/delete 使用 owner_id。
- resume_id 格式和路径校验。
- Pydantic 严格校验 LLM 输出。
- JD evidence 必须存在于原文。
- career_llm_enabled 默认关闭。
- 错误使用具体异常和可行动上下文。
- 日志避免打印原文。
- 缺资源、缺参数和模型失败不会静默变成成功。

### 9.2 MVP 仍然存在的风险

必须诚实说明以下限制：

- 原始简历暂时以本地文件保存，尚未实现加密。
- 尚未实现自动过期和保留期限。
- 尚未实现组织级、多租户、管理员级权限。
- PII 识别主要依赖规则，不是完整 NER。
- 图片和扫描 PDF 中的隐私还未处理。
- 尚未建立完整的合规审计日志。
- 如果未来把 raw text 发送给外部模型，需要重新设计授权、数据协议和脱敏策略。

面试时主动说明这些边界，比声称“已经完全保证隐私”更可靠。

### 9.3 错误处理原则

- 捕获具体异常，例如 ResumeParseError、ResumeNotFound 和 CareerAgentError。
- 错误信息包含操作、资源 ID、状态码或响应片段等上下文。
- 不用空结果伪装成功。
- 不静默吞掉异常。
- 可回退时记录 warning，并表明使用了哪个抽取器。
- 不可回退时明确返回 failed。
- 模型失败不应该导致未经验证的报告进入用户界面。

当前 ModelClient 延续项目已有同步边界。若进入高并发生产环境，应把模型调用和较重的解析任务放到异步 worker，并增加超时、重试、指数退避和取消机制。

## 11. 模拟求职面试问答

### 问题 1：为什么阶段二之后还需要 CareerAgent？

答：阶段二主要回答市场问题，例如哪些岗位存在、哪些技能常见、薪资如何；CareerAgent 连接个人简历和市场画像，回答简历覆盖哪些要求、证据在哪里、怎样改写和准备面试。没有它，系统只是职位搜索和统计工具，而不是求职辅助 Agent。

### 问题 2：为什么不直接让大模型打匹配分？

答：直接打分会产生不可验证结论、别名匹配不稳定、隐私暴露和模型失败风险。当前实现先建立 canonical skill、EvidenceRef、统计分母和覆盖状态，再让 LLM 做可选增强。这样可以解释每项结论，也可以在关闭 LLM 时继续工作。

### 问题 3：ResumeEvidence 为什么不保存完整简历文本？

答：完整文本可以作为受控的本地 raw source 保存，但下游分析使用脱敏后的最小结构化证据。这样减少 PII 在日志、API 和多个模块之间传播，也让报告中的结论更容易定位和复核。需要展示原文时，应通过有权限的受控读取，而不是复制到所有对象中。

### 问题 4：如何降低简历隐私发送给 LLM 的风险？

答：上传后先在本地执行 PII 脱敏，再抽取 evidence。模型只接收必要的脱敏文本或结构化字段，默认不接收 raw source。邮箱、电话和身份证号等由本地规则处理。但这只是风险降低，不是绝对保证；扫描图像和未标注实体仍需要更强的识别和合规措施。

### 问题 5：扫描 PDF 怎么处理？

答：先限制文件字节数和页数，再用 pypdf 提取文本。如果提取后为空或低于最小文本长度，就显式抛出解析错误，不把空内容送给模型。未来可以加 OCR，但 OCR 也需要超时、页数、隐私和人工复核边界。

### 问题 6：为什么默认使用正则而不是默认调用 LLM？

答：正则和技能目录可离线、可复现、低成本，适合作为可靠基线。LLM 有延迟、成本、隐私和输出不确定性。career_llm_enabled 显式开启后才使用模型增强，而且输出要过 schema 和 evidence 验证。

### 问题 7：技能别名归一化解决什么问题？

答：它把 K8s 和 Kubernetes、Python3 和 Python 等表面不同的名称映射到同一个 canonical key，避免 false missing 和重复统计。比较和统计用 canonical key，展示用 display name，证据保留原始文本。

### 问题 8：为什么验证 LLM 的 evidence 必须是 JD 原文子串？

答：模型可能凭常识补全 JD 中没有的技能。要求 evidence 是原文子串，可以区分“模型推测”与“职位描述真实写出”。这不能保证模型完全正确，但能消除一类直接的技能幻觉。

### 问题 9：must_have、preferred 和 unknown 如何判断？

答：查看技能附近的局部上下文。“必须、要求、掌握”倾向 must_have；“优先、加分、熟悉即可”倾向 preferred；上下文不足则 unknown。实现是启发式规则，所以要保留原文 evidence，不能把它说成招聘方的绝对承诺。

### 问题 10：技能出现率的分母是什么？

答：是筛选后、能成功解析职位描述的有效 JD 数量。公式是包含技能的有效 JD 数量除以 valid_jd_count。不能使用所有职位数，也不能用词频作为分母，否则没有可用文本的职位会扭曲结果。

### 问题 11：covered、partial、missing 如何定义？

答：covered 表示有归一化技能且有相关简历证据；partial 表示有技能或项目线索但深度、上下文或结果不足；missing 表示当前 evidence 中没有找到该技能或相关项目。missing 是证据缺失，不是对求职者能力的绝对否定。

### 问题 12：为什么简历技能列表里有一个词不能直接判定 covered？

答：技能列表只能说明用户写过这个词，不能证明实际使用深度。例如“熟悉 Kubernetes”不等于“独立维护生产集群”。系统应结合项目行、职责和量化结果，必要时判为 partial，并建议补充范围和成果。

### 问题 13：如何防止报告编造项目成果？

答：facts 必须来自 ResumeEvidence、JobProfile 和市场统计；建议可以要求用户补充真实指标，但不能直接写出简历中不存在的用户量、性能提升或上线职责。没有数字时应该说“补充真实指标”，不能自行填数字。

### 问题 14：为什么统计薪资、经验和学历？

答：技能覆盖只反映能力要求，薪资和经验学历分布帮助用户理解目标市场和筛选门槛。但它们是给定数据快照下的市场描述，不是 offer 保证，也不是个人薪资预测。报告需要同时展示样本量、单位和低样本 warning。

### 问题 15：样本很小怎么办？

答：仍可展示结果，但 JobProfile 保存 valid_jd_count，并在少于 10 条时增加 warning。措辞应是“当前 6 条样本中观察到”，不能说“市场普遍要求”。以后可以加入置信区间、时间窗口和分层分析。

### 问题 16：如何保证用户不能读取别人的简历？

答：ResumeStore 的 load 和 delete 都接收 owner_id，目录按 owner_id/resume_id 组织，resume_id 还要做格式和路径解析校验。对不存在和不属于当前用户的 ID，外部响应应尽量一致，避免资源枚举。

### 问题 17：为什么上传读取采用分块和超限立即失败？

答：这样不需要把一个未知大小文件完整读入后才检查，可以降低内存消耗和拒绝服务风险。当前合法文件上限较小，会在内存中拼接；如果文件继续变大，应改为临时文件和流式 hash。

### 问题 18：LLM 不可用时职业分析会不会完全失败？

答：默认不会，因为默认使用确定性的技能目录、正则和统计。显式启用 LLM 后，可以在可接受的职位技能抽取场景回退到正则并记录 warning；如果调用方要求完整高精度，也可以返回 failed。关键是不静默生成缺少事实验证的报告。

### 问题 19：为什么缺少 target 或 resume_id 时返回 clarify？

答：没有 target 就无法构建目标 JobProfile，没有 resume_id 就不知道分析哪份简历。自动猜测会造成错误目标或越权，所以工作流应明确列出缺少的参数，请用户补充。

### 问题 20：为什么 Coordinator 和 CareerAgent 要分开？

答：Coordinator 负责资源状态、权限、数据集和工作流；CareerAgent 只负责已准备证据之间的分析。这样便于独立测试、替换存储、加入任务队列，也避免 Agent 内部混入文件系统和权限逻辑。

### 问题 21：如果进入高并发服务，哪些地方要异步化？

答：当前 ModelClient 是同步边界，适合 MVP。生产版可以把 PDF 解析、LLM 调用和画像计算放到异步 worker，接口返回任务 ID，再提供状态查询。需要增加超时、指数退避、取消和幂等；数据契约可以继续复用。

### 问题 22：阶段三最重要的测试是什么？

答：不是只有正常输入，而是安全和边界：超大文件、扫描 PDF、PII 不进入 evidence、伪造 evidence 被拒绝、owner 隔离、低样本 warning、缺参数 clarify、没有证据不能 covered、报告不能产生虚构数字。这些测试直接验证了系统的可靠性目标。

### 问题 23：阶段三哪些功能还没有实现？

答：没有 OCR、DOCX、自动投递、在线实时抓取、加密存储、自动过期、完整多租户权限和经过标注评估的总匹配分数。MVP 先保证证据链和确定性基础，后续应根据真实数据和用户反馈决定扩展顺序。

### 问题 24：如何评价这一阶段是否成功？

答：不能只看接口返回 200。还要看 schema 稳定性、证据定位准确率、隐私隔离、结果可复现性、模型失败可控性、低样本提示以及建议是否真的帮助用户修改简历和准备面试。下一步可建立人工标注集，评估技能抽取 precision/recall、覆盖度一致性和建议事实忠实度。

## 12. 局限和下一步

### 12.1 当前局限

- 技能目录和别名表有限，长尾技能可能漏检。
- 正则对复杂否定句和隐含能力理解有限。
- PDF 只处理文本层，不处理扫描图像。
- PII 主要依赖规则，不能覆盖所有实体。
- 原始文件还没有加密和过期删除。
- 薪资结果依赖 ETL 字段质量和单位统一。
- small sample warning 不是完整统计推断。
- LLM 建议仍需人工评估。
- 当前没有经过真实数据验证的总匹配评分。

### 12.2 推荐迭代顺序

1. 建立人工标注的 JD 技能和简历技能集合。
2. 对 regex、LLM 和混合抽取评估 precision、recall。
3. 增加 DOCX 和 OCR，但保持严格资源限制。
4. 增加加密、保留期限、用户删除和审计机制。
5. 将模型调用迁移到异步 worker，支持超时、重试和取消。
6. 建立报告版本和 extractor_version 重算机制。
7. 用用户反馈评估建议是否改善简历和面试表现。
8. 只有在有足够标注和反馈后，才引入可解释匹配评分。

## 13. 面试前快速复习

    文件上传
      → 有界读取
      → 格式、大小、页数、文本校验
      → 本地 PII 脱敏
      → ResumeEvidence
      → owner-scoped ResumeStore
      → 读取发布的职位数据
      → SkillCatalog 归一化
      → valid_jd_count 和 occurrence_rate
      → JobProfile
      → covered / partial / missing
      → 带 EvidenceRef 的 CareerReport

五个最重要的原则：

1. 先证据，后结论：报告不能脱离原始依据。
2. 先确定性底座，后可选 LLM：模型不能替代权限、统计和事实验证。
3. 默认最小暴露：raw source、redacted text、evidence 分层保存。
4. missing 不等于不会：它只表示当前材料缺少可验证证据。
5. 失败要显式：解析失败、模型失败、资源缺失和权限失败不能伪装成功。

阶段三真正完成的不是“让模型生成一段职业建议”，而是建立从个人材料到招聘市场、从市场统计到可执行建议的第一条可审计链路。
