## 1. 阶段二的任务、作用与必要性

### 1.1 阶段二在整个 OfferAgent 中的位置

项目的主链路是：

    BOSS 岗位采集
        ↓
    阶段一：ETL、薪资数值化、字段规范化、版本化 CSV/Schema
        ↓
    阶段二：Coordinator 路由 + QueryAgent NL2SQL + SQL 安全校验/执行/自修正
        ↓
    阶段三：CareerAgent 读取岗位画像和简历证据，生成技能缺口与求职报告

阶段一解决的是“数据能否被稳定、可重复地查询”。它把原始岗位 JSON 转成了四张可供 DuckDB 读取的 CSV，并生成 schema、crawl_runs 和数据集版本。

阶段二解决的是“用户的问题能否安全、可解释地变成一次查询”：

- 用户可以用自然语言询问薪资、城市、技能、学历、经验等岗位市场问题。
- 模型只能根据经过权限过滤的完整 Schema 生成 SQL。
- SQL 在执行前通过 sqlglot 和 DuckDB 规则校验。
- 执行失败时，只把可修复的错误反馈给模型，最多进行两次修复。
- 每一次 SQL 尝试、校验、执行和修复都可以作为结构化事件展示给前端。
- career_advice 任务先检查城市、简历和岗位数据的新鲜度，再决定澄清、请求采集还是进入后续分析。

设计文档在技术决策中明确选择“全量表结构注入 Prompt，不做 Schema RAG”，并把 SQL Self-Correction、Coordinator 资源门控和受限 ChartSpec 列为阶段二的重点。

### 1.2 为什么阶段一之后还需要独立的阶段二

#### 问题一：模型不知道数据库的准确字段

自然语言中说“薪资”“学历”“岗位详情”，数据库中可能对应：

    jobs.salary_min_k
    jobs.salary_max_k
    jobs.degree
    job_details.jd_text

如果把原始 CSV 或零散字段描述直接交给模型，模型容易产生不存在的列名，或者把列表表和详情表的粒度混淆。阶段二用确定性的 SchemaCatalog 统一提供表名、字段类型、中文含义、别名、聚合能力、样例值和表关系。

#### 问题二：模型生成的 SQL 即使看起来合理，也不可信

模型可能生成：

    SELECT * FROM jobs;

也可能生成：

    DELETE FROM jobs;

或者引用不存在的表、文件路径和跨库对象。SQL 是可执行代码，不能把“模型说它是查询”当作安全证明。因此必须把 SQL 解析、只读约束、表白名单、字段显式列出、访问权限和执行行数上限放在模型之外，由确定性代码完成。

#### 问题三：一次生成失败不应等于整个任务失败

自然语言到 SQL 的错误经常是局部的。例如模型把 salary_min_k 写成了 salary_min，这类未知字段错误可以把失败 SQL 和有限错误信息回喂模型修正。但如果是权限错误或安全策略错误，继续让模型“想办法绕过”反而扩大风险。因此阶段二需要一个有限且分类明确的修复环，而不是无限重试。

#### 问题四：求职分析需要先检查资源

“帮我分析上海 Python 工程师岗位”不是只生成一条 SQL：

- 目标城市是否明确？
- 是否已有简历？
- 是否存在匹配关键词和城市的数据集？
- 最近一次成功采集是否超过 7 天？
- 是否应该请求独立采集任务？

这些判断属于 Coordinator 的资源门控，不应混在 QueryAgent 的 SQL 生成逻辑里。

#### 问题五：前端需要看到过程，但不能看到模型隐藏思维链

用户需要知道“Schema 已加载、SQL 已生成、正在校验、修复了一次、查询完成”，但不应该把模型内部的长篇推理暴露为产品协议。阶段二因此定义了结构化 Query 事件，只公开必要的状态、SQL、错误类别和结果统计。

### 1.3 阶段二的任务与产物

| 任务 | 主要产物 | 解决的问题 |
|---|---|---|
| 定义 Query 契约 | QueryPlan、SchemaCatalog、SqlAttempt、QueryAgentResult | Agent 之间不再传递无约束字典 |
| 构造完整 Schema | SchemaCatalogBuilder、SchemaCatalog | 减少模型臆造表名和字段名 |
| 实现 SQL 闭环 | QueryAgent.run() / arun() | 把生成、校验、执行、修复放进一个有界流程 |
| 错误分类 | SqlErrorKind、classify_sql_error() | 决定什么错误可修复、什么错误必须停止 |
| 接入只读执行器 | DuckDbEngine.validate_sql()、execute() | 防止写操作、跨库访问、未授权表和文件函数 |
| 发布结构化事件 | QueryEventType、event_sink | 支持 SSE/轮询消费执行轨迹 |
| 增加岗位资源门控 | Coordinator、RouteDecision | 在查询前处理城市、简历和数据新鲜度 |
| 扩展图表 | ChartSpec、chart_spec_to_echarts() | 禁止模型直接生成任意 ECharts option |
| 前后端接入 | QueryState、QueryResult、Vue 图表组件 | 把阶段二结果展示给用户 |
| 阶段性测试 | tests/test_stage2.py | 证明关键安全和修复边界成立 |

### 1.4 阶段二的输入、输出与边界

输入：

- 阶段一生成的 jobs_market CSV 和 schema
- 经过预处理的用户问题或 QueryPlan
- 当前用户的 AccessScope
- 可选的模型客户端
- 可选的历史采集状态 crawl_runs.csv

输出：

- 成功时：SQL、列名、最多 200 行结果、数据集版本、Schema token 估算、SQL 尝试记录
- 失败时：稳定的错误类别、有限错误摘要、已经发生的尝试
- 工作流层输出：QueryResult 和 execution_log
- 前端可消费：结构化 Query 事件、图表业务契约

明确不属于当前阶段的内容：

- 不在 HTTP 请求线程中直接运行 BOSS 采集。
- 不让 Coordinator 直接执行 SQL。
- 不让 QueryAgent 修改数据库。
- 不在本阶段实现完整的简历解析、JD 技能抽取和证据覆盖分析。
- 不把“模型生成了 SQL”当作安全检查完成。
- 不把 token 估算值误报为某一家模型供应商的精确 tokenizer 计数。

## 2. 整体架构与代码地图

### 2.1 阶段二的主流程

    用户自然语言问题
        ↓
    Preprocessor：识别意图、生成独立查询、提取参数
        ↓
    ┌─────────────────────────────┐
    │ database_query + jobs_market │ → QueryAgent
    │ career_advice                │ → Coordinator
    │ 其它旧 AskData 流程          │ → 兼容查询路径
    └─────────────────────────────┘

    QueryAgent
        ↓
    SchemaCatalogBuilder
        ↓
    权限过滤后的完整 SchemaCatalog
        ↓
    模型结构化生成 SQL
        ↓
    DuckDBEngine.validate_sql
        ├─ 失败且可修复 → 有界修复上下文 → 再生成
        └─ 通过
             ↓
         DuckDBEngine.execute
             ├─ 成功 → QueryAgentResult
             ├─ 可修复错误 → 有界修复上下文
             └─ 安全/权限/不可修复/耗尽 → 失败结果

    Coordinator
        ↓
    解析关键词、城市、简历
        ↓
    资源检查
        ├─ 缺少参数 → waiting_clarification
        ├─ 没有或过期数据 → request_crawl
        └─ 数据可用 → 后续 Query/Career 流程

主链路的关键边界是：

1. Preprocessor 负责意图、独立查询和参数初步解析。
2. Coordinator 负责资源和路由，不执行 SQL。
3. QueryAgent 负责 SQL 生成、校验、执行和自修正，不负责爬虫和职业报告。
4. DuckDbEngine 负责确定性的 SQL 安全检查和只读执行。
5. ChartSpec 只描述业务图表，ECharts option 由程序确定性生成。

### 2.2 代码地图

| 文件 | 职责 | 重点对象 |
|---|---|---|
| backend/app/contracts.py | Agent、SQL、事件和结果契约 | QueryPlan、SchemaCatalog、SqlAttempt、QueryEventType |
| backend/app/querying/schema_catalog.py | 从数据集 Schema 构造完整 Prompt 上下文 | SchemaCatalogBuilder.build() |
| backend/app/querying/query_agent.py | NL2SQL 闭环和修复 | QueryAgent.run()、_generate() |
| backend/app/querying/sql_errors.py | SQL 错误归一化 | classify_sql_error()、bounded_error() |
| backend/app/querying/duckdb_engine.py | CSV 视图、SQL 校验和执行 | validate_sql()、execute()、connect() |
| backend/app/coordinator.py | 求职任务参数解析、数据新鲜度检查和路由 | parse_target()、inspect_dataset()、decide() |
| backend/app/querying/charting.py | ChartSpec 到 ECharts option 的确定性转换 | chart_spec_to_echarts() |

### 2.3 一次查询的生命周期

以“查询上海 Python 工程师的平均薪资”为例：

    1. 用户提交任务
    2. Preprocessor 判断 action = database_query
    3. 工作流检查 access_scope 是否只允许 jobs_market
    4. 进入 QueryAgent
    5. SchemaCatalogBuilder 加载四张表和 66 个字段
    6. 记录 query.schema_loaded
    7. 模型生成一条结构化 SqlGeneration
    8. 记录 query.sql_generated
    9. DuckDBEngine.validate_sql() 做只读和权限校验
    10. 记录 query.sql_validated
    11. DuckDBEngine.execute() 执行 CSV 视图查询
    12. 记录 query.sql_executed
    13. 成功则记录 query.completed
    14. 工作流把结果、attempts、dataset_version 和 execution_log 写入 QueryResult

如果第 9 或第 11 步出现可修复错误，则进入有限修复环；如果出现安全错误、权限错误或尝试次数耗尽，则记录 query.failed 并如实返回失败。

## 3. 跨模块契约：为什么先定义数据结构

### 3.1 Agent 系统最容易失控的地方

如果 Agent 之间直接传递普通 dict，以下错误只能在运行很深之后才暴露：

- attempt 传成字符串或从 0 开始。
- status 拼写不一致。
- SQL 生成返回 Markdown 代码块、列表或缺失 sql 字段。
- 结果中混入未经限制的任意 ECharts option。
- 查询失败后，调用方不知道错误是否允许重试。

阶段二在 contracts.py 中为这些边界建模。Pydantic 模型的意义不是“让代码更漂亮”，而是把外部模型输出和跨模块状态转成可验证的运行时协议。

### 3.2 QueryPlan：QueryAgent 的最小输入

    class QueryPlan(BaseModel):
        query: str = Field(min_length=1, max_length=5000)
        database: str = Field(default="", max_length=100)
        dataset_version: str | None = Field(default=None, max_length=200)
        filters: list[str] = Field(default_factory=list, max_length=50)
        metrics: list[str] = Field(default_factory=list, max_length=50)
        dimensions: list[str] = Field(default_factory=list, max_length=50)

        @field_validator("query")
        @classmethod
        def query_must_not_be_blank(cls, value: str) -> str:
            value = value.strip()
            if not value:
                raise ValueError("查询问题不能为空")
            return value

字段说明：

| 字段 | 作用 |
|---|---|
| query | 原始或独立改写后的自然语言问题 |
| database | 指定数据库；为空时由 QueryAgent 根据权限或默认值选择 |
| dataset_version | 可用于结果追踪；当前 QueryAgent 会以实际 Schema 版本为主 |
| filters | 结构化过滤提示，例如城市或经验 |
| metrics | 用户要求的指标，例如平均薪资、P75 |
| dimensions | 分组维度，例如城市、学历 |

QueryPlan 只描述查询意图，不接受模型生成的 SQL。SQL 生成属于 QueryAgent 内部的下一步，避免让上游状态伪装成已校验 SQL。

### 3.3 SqlGeneration：模型输出的窄契约

    class SqlGeneration(BaseModel):
        sql: str = Field(min_length=1, max_length=20000)
        explanation: str = Field(default="", max_length=1000)

模型必须返回 JSON 对象，至少有一个非空 sql 字段。explanation 只作为简短展示信息，不能被当作安全证明。模型可能仍然返回错误 SQL，所以结构化输出只解决“格式可靠性”，不解决“语义和安全可靠性”。

### 3.4 SqlAttempt：把每一次尝试记录下来

    class SqlAttempt(BaseModel):
        attempt: int = Field(ge=1, le=3)
        sql: str = Field(min_length=1, max_length=20000)
        validation: SqlValidation
        execution: SqlExecution
        error_kind: SqlErrorKind | None = None
        retryable: bool = False

这里的 attempt 上限直接写进了 Pydantic 约束；QueryAgent 还会在运行逻辑中使用 MAX_ATTEMPTS = 3。二者都存在是有意的：

- 模型层防止有人构造超过上限的结果。
- 运行层防止循环真的执行超过上限。

validation 和 execution 分开记录，能够区分：

- SQL 还没有执行，就被安全规则拒绝。
- SQL 通过了安全校验，但 DuckDB 绑定或读取时失败。
- SQL 通过校验并执行成功。

### 3.5 错误类别和事件类别

    class SqlErrorKind(StrEnum):
        SYNTAX = "syntax"
        UNKNOWN_FIELD = "unknown_field"
        UNKNOWN_TABLE = "unknown_table"
        TYPE_BINDING = "type_binding"
        PERMISSION = "permission"
        SECURITY = "security"
        DATABASE_NOT_FOUND = "database_not_found"
        TIMEOUT = "timeout"
        EMPTY_RESULT = "empty_result"
        MODEL_UNAVAILABLE = "model_unavailable"
        UNKNOWN = "unknown"

可修复错误集合只有：

    _RETRYABLE = {
        SqlErrorKind.SYNTAX,
        SqlErrorKind.UNKNOWN_FIELD,
        SqlErrorKind.UNKNOWN_TABLE,
        SqlErrorKind.TYPE_BINDING,
    }

事件类型使用稳定字符串：

    class QueryEventType(StrEnum):
        SCHEMA_LOADED = "query.schema_loaded"
        SQL_GENERATED = "query.sql_generated"
        SQL_VALIDATED = "query.sql_validated"
        SQL_EXECUTED = "query.sql_executed"
        SQL_REPAIR = "query.sql_repair"
        COMPLETED = "query.completed"
        FAILED = "query.failed"

事件类别和错误类别的区别是：

- SqlErrorKind 描述失败原因和是否可修复。
- QueryEventType 描述工作流当前走到了哪一步。

### 3.6 QueryAgentResult：对 Coordinator 和 SSE 的输出

成功结果会包含：

- query
- database
- dataset_version
- status = completed
- sql
- columns
- rows
- attempts
- schema_catalog

失败结果会包含：

- status = failed
- 已经发生的 attempts
- error_kind
- 有界的 error
- 如果已经成功加载，则仍保留 schema_catalog

其中模型字段使用 schema_catalog，并以别名 schema 兼容现有代码；属性 schema 只提供读取便利。这样可以避免 Pydantic 对 schema 内部名称产生的潜在冲突，同时让工作流代码可以读取 result.schema.prompt_token_count。

### 3.7 ChartSpec：图表也必须是受限契约

    class ChartSpec(BaseModel):
        type: Literal["bar", "pie", "line", "histogram"]
        title: str
        source_task_id: str
        category_field: str
        value_field: str
        max_items: int = Field(default=12, ge=3, le=30)
        bins: int = Field(default=10, ge=3, le=50)

模型只能指定图表类型和数据字段，不能直接提交任意 JavaScript、颜色回调或事件处理器。后端根据这个契约生成 ECharts option。

## 4. Schema Catalog：为什么不用 Schema RAG

### 4.1 设计决策

早期 AskData 代码有 Schema 检索能力，包括索引、BM25/稠密检索、RRF 和 rerank。设计文档在阶段二明确选择：

    全量表结构注入 Prompt，不做 Schema RAG。

原因不是“RAG 没有价值”，而是当前数据规模适合全量注入：

- 阶段一的 jobs_market 实测只有 4 张表、66 个字段。
- Schema 文本是结构化、稳定、可审计的上下文，不是大规模非结构化文档。
- 移除 embedding/rerank 可以减少外部 API 依赖、检索延迟和失败面。
- 全量注入能让模型同时看到表之间的关系，降低只检索到半个 JOIN 关系的风险。
- 阶段二可以直接测量 Prompt 规模和查询准确率，为以后是否引入检索提供基线。

这是一种基于当前规模的工程取舍，而不是永久宣称“所有数据库都不需要 Schema RAG”。如果未来表和字段数量显著增大，应使用评测数据比较全量注入、分层 Schema、表级召回和字段级召回。

### 4.2 SchemaCatalogBuilder 的职责

入口函数：

    def build_schema_catalog(
        database: str,
        database_root: Path | None = None,
        access_scope: AccessScope | dict[str, Any] | None = None,
    ) -> SchemaCatalog:
        return SchemaCatalogBuilder(database_root).build(database, access_scope)

类的构造函数：

    class SchemaCatalogBuilder:
        def __init__(self, database_root: Path | None = None) -> None:
            self.engine = DuckDbEngine(database_root)

database_root 的作用是指定本地数据库根目录。没有传入时使用 DuckDbEngine 的默认路径。构造 Builder 时复用同一个数据库根目录，避免 Schema 读取和实际 SQL 执行指向不同目录。

核心方法：

    def build(
        self,
        database: str,
        access_scope: AccessScope | dict[str, Any] | None = None,
    ) -> SchemaCatalog:

参数说明：

| 参数 | 作用 |
|---|---|
| database | 需要查询的逻辑数据库，例如 jobs_market |
| access_scope | 可为 AccessScope 或字典；用于过滤数据库和数据表 |
| 返回值 | 经过权限过滤并完成 Prompt 统计的 SchemaCatalog |

### 4.3 Schema 的来源和权限过滤

对 jobs_market，Builder 优先加载阶段一生成的 schema：

    if database == "jobs_market" and (folder / "_schema.json").exists():
        market = load_market_schema(folder)
        return (
            [table.model_dump(mode="json") for table in market.tables],
            market.dataset_version,
            [relation.model_dump(mode="json") for relation in market.relations],
        )

这保证了 Prompt 中的字段定义和实际 CSV 发布版本一致。其它旧数据库仍可以从应用内的静态 SCHEMA 和 RELATIONS 读取，这是为了兼容 AskData 示例。

权限处理发生在表和关系两个层次：

1. 如果 access_scope 不允许访问数据库，立即抛出 PermissionError。
2. 对每张表调用 scope.allows_table(database, table_id)。
3. 只保留两端都可见的关系，避免把被禁止表的信息泄漏到 Prompt。

这一步很重要：如果先把完整 Schema 注入，再依赖模型“自觉不使用某张表”，权限边界就已经晚了。

### 4.4 字段信息包含什么

每个 SchemaCatalogField 包含：

| 字段 | 说明 |
|---|---|
| table | 物理表名 |
| name | SQL 字段名 |
| label | 中文或业务标签 |
| type | 业务类型，例如数值、日期、文本 |
| source_type | 实际 SQL 类型，例如 DOUBLE、VARCHAR |
| description | 业务含义 |
| aliases | 用户常用别名 |
| role | 维度、指标等角色 |
| aggregation | 可用聚合方式 |
| samples | 少量样例值 |
| data_profile | 阶段一生成的数据画像 |

敏感字段不会把样例值写入 Prompt：

    _SENSITIVE_SAMPLE_FIELDS = {
        "jd_text", "evidence_text", "job_link", "company", "title"
    }

这里的设计不是把字段隐藏掉。模型仍然需要知道 jd_text 存在，才能判断是否可以查询它；只是不能把完整 JD、证据文本、链接和公司/岗位名称样例批量放入提示词，减少 Prompt 体积和不必要的数据暴露。

### 4.5 稳定渲染：render() 和 to_prompt()

SchemaCatalog.render() 负责把对象变成稳定顺序的文本：

    def render(self) -> str:
        lines = [
            f"数据库：{self.database}",
            f"数据集版本：{self.dataset_version}",
            "仅允许生成一条 DuckDB SELECT/WITH 只读 SQL；"
            "必须显式列出字段，禁止 SELECT *。",
        ]
        for table in sorted(self.tables, key=lambda item: item.name):
            lines.append(
                f"表 {table.name}（{table.label}，{table.row_count} 行）："
                f"{table.description}"
            )
            ...
        for relation in self.relations:
            lines.append(...)
        return "\n".join(lines)

稳定顺序有两个工程价值：

- 同一个数据集每次生成的 Prompt 不会因为文件遍历顺序不同而漂移。
- 评测和缓存可以更容易比较 Prompt 变化。

to_prompt() 当前是 render() 的语义别名，便于调用方按“把 Schema 转为 Prompt”来理解。

### 4.6 实际 token 规模怎么测

当前实现没有额外引入供应商 tokenizer，而是使用可复现的估算：

    def with_prompt_stats(self) -> "SchemaCatalog":
        rendered = self.render()
        return self.model_copy(
            update={
                "prompt_char_count": len(rendered),
                "prompt_token_count": max(1, math.ceil(len(rendered) / 4)),
            }
        )

这表示：

    prompt_char_count = len(rendered)
    prompt_token_count = ceil(prompt_char_count / 4)

这是项目内的估算值，不是某个模型服务商的精确 token 数。笔记、日志和面试中应准确称为“字符数 / 4 的可复现估算”，不能说“已经调用了 tokenizer 得到精确 token”。

阶段二的本地样本中，完整 Catalog 为 4 张表、66 个字段；实际数字应以当前运行环境中的 schema 和 render() 结果为准。结果会把 dataset_version 和 prompt_token_count 传给工作流，以便前端或评测记录。

## 5. QueryAgent：NL2SQL 的完整执行闭环

### 5.1 Agent 的职责边界

QueryAgent 的职责是：

    自然语言 QueryPlan
        → 加载权限过滤后的 SchemaCatalog
        → 模型生成结构化 SQL
        → sqlglot/DuckDB 安全校验
        → 只读执行
        → 对可修复错误进行有限修复
        → 返回 QueryAgentResult

它不负责：

- 识别所有业务意图；
- 运行爬虫；
- 上传或解析简历；
- 生成最终职业报告；
- 绕过访问控制；
- 修改数据库。

### 5.2 构造函数和依赖注入

    def __init__(
        self,
        model_client: ModelClient,
        engine: DuckDbEngine | None = None,
        catalog_builder: SchemaCatalogBuilder | None = None,
        *,
        max_attempts: int = MAX_ATTEMPTS,
        sql_generator: SqlGenerator | None = None,
    ) -> None:

参数说明：

| 参数 | 作用 |
|---|---|
| model_client | 默认 SQL 生成器使用的模型客户端 |
| engine | SQL 校验和只读执行器；默认创建 DuckDbEngine |
| catalog_builder | Schema 构造器；默认复用 engine 的数据库根目录 |
| max_attempts | 最大尝试次数，必须在 1～3 之间 |
| sql_generator | 可选的可注入生成函数，主要用于测试和确定性回归 |

sql_generator 是很有价值的测试设计。单元测试不需要真实调用 LLM，只需按调用次数返回预先安排的 SQL，就能稳定测试：

- 首轮未知字段，第二次修复成功；
- 安全错误不能重试；
- 连续三次错误后停止；
- 不会因为模型返回第四个 SQL 而突破上限。

### 5.3 run() 的输入与输出

    def run(
        self,
        plan: QueryPlan | str | dict[str, Any],
        database: str | None = None,
        *,
        access_scope: AccessScope | dict[str, Any] | None = None,
        event_sink: EventSink | None = None,
    ) -> QueryAgentResult:

输入支持三种形式：

- 已校验的 QueryPlan
- 自然语言字符串
- 普通字典，由 QueryPlan.model_validate() 运行时校验

database 是兼容参数。如果 run() 的 database 参数非空，优先使用该参数；否则使用 plan.database；如果两者都没有，则：

1. 使用 access_scope.allowed_databases 中排序后的第一个数据库；
2. 否则默认 jobs_market。

event_sink 的签名是：

    Callable[[str, dict[str, Any]], None]

它允许工作流把 QueryAgent 的中间事件收集到 execution_log 或写入统一事件存储。

### 5.4 第一步：加载 Schema

    catalog = self.catalog_builder.build(selected_database, access_scope)

加载成功后发出：

    self._emit(
        event_sink,
        QueryEventType.SCHEMA_LOADED,
        {
            "database": selected_database,
            "dataset_version": catalog.dataset_version,
            "table_count": len(catalog.tables),
            "field_count": len(catalog.fields),
            "prompt_char_count": catalog.prompt_char_count,
            "prompt_token_count": catalog.prompt_token_count,
        },
    )

如果加载失败，QueryAgent 不会调用模型“猜一个数据库”。它将错误转换成失败结果，并保留已经创建的尝试列表。

### 5.5 第二步：生成结构化 SQL

默认生成路径在 _generate() 中构造系统提示：

    system = (
        "你是严格的 NL2SQL 生成器。只能输出 JSON："
        '{"sql":"一条SELECT或WITH SQL","explanation":"简短说明"}。'
        "SQL 必须只使用下面完整 Schema 中的表和字段，显式列出字段，禁止 SELECT *、"
        "多语句、写操作、文件函数和跨库引用。"
        + chr(10)
        + catalog.render()
    )

首次生成时，用户载荷包括：

    {
        "query": plan.query,
        "filters": plan.filters,
        "metrics": plan.metrics,
        "dimensions": plan.dimensions,
    }

模型返回值先经过 isinstance(payload, dict) 检查，再经过：

    return SqlGeneration.model_validate(payload)

这两层检查分别处理：

- 返回值根本不是 JSON 对象；
- JSON 对象缺少 sql、字段为空或超过长度限制。

如果模型客户端抛出 RuntimeError，QueryAgent 将其归类为 model_unavailable，不会自动把模型不可用当成 SQL 错误重试。

### 5.6 第三步：发出 SQL 生成事件

每次生成后都会发送：

    {
        "attempt": attempt_number,
        "sql": sql,
        "explanation": generated.explanation,
    }

事件只展示生成结果和简短说明，不包含模型隐藏思维链。attempt 从 1 开始，修复生成也会再次发出 query.sql_generated。

### 5.7 第四步：校验 SQL

    safe_sql = self.engine.validate_sql(
        selected_database,
        sql,
        self._scope(access_scope),
    )

校验通过后发出：

    {
        "attempt": attempt_number,
        "validation": "passed",
    }

校验失败则生成一个 SqlAttempt：

    record = SqlAttempt(
        attempt=attempt_number,
        sql=sql,
        validation=SqlValidation.REJECTED,
        execution=SqlExecution.FAILED,
        error_kind=kind,
        retryable=retryable,
    )

然后根据 retryable 决定是否修复。

### 5.8 第五步：只读执行

校验通过后，QueryAgent 调用：

    execution = self.engine.execute(
        selected_database,
        safe_sql,
        self._scope(access_scope),
    )

成功时会记录：

    SqlAttempt(
        attempt=attempt_number,
        sql=safe_sql,
        validation=SqlValidation.PASSED,
        execution=SqlExecution.SUCCEEDED,
    )

并返回：

- columns
- rows
- dataset_version
- attempts
- schema

DuckDB 引擎当前最多读取 201 行，再截取前 200 行：

    raw_rows = cursor.fetchmany(201)
    rows = [...]

这既是输出边界，也是避免一次查询把过大结果集直接塞进任务状态的防护。

### 5.9 异步入口 arun()

    async def arun(self, *args: Any, **kwargs: Any) -> QueryAgentResult:
        return await asyncio.to_thread(self.run, *args, **kwargs)

DuckDB 本地执行和当前模型客户端接口是同步的。arun() 使用线程池把同步闭环移出 FastAPI/LangGraph 事件循环，避免一个查询阻塞其它异步请求。

它不是把同步函数“伪装成异步”就结束了：后续如果模型客户端原生支持 async，应把 _generate() 的模型调用替换为真正的异步接口；目前 arun() 是兼容现有同步依赖的明确过渡层。

## 6. DuckDB 与 SQL 安全校验

### 6.1 validate_sql() 和 execute() 的职责分离

DuckDbEngine 对外提供：

    def validate_sql(
        self,
        database: str,
        sql: str,
        access_scope: AccessScope | None = None,
    ) -> str:

以及：

    def execute(
        self,
        database: str,
        sql: str,
        access_scope: AccessScope | None = None,
    ) -> SqlExecution:

职责分工：

- validate_sql() 只解析和检查，不访问查询结果。
- execute() 再次调用内部校验，然后在内存 DuckDB 连接上执行。

执行时再次校验是有意的防御性设计。即使未来某个调用方绕过 QueryAgent 直接调用 execute()，也不能跳过 SQL 安全守卫。

### 6.2 sqlglot 校验规则

当前 _validate_sql() 的主要规则如下：

1. 去掉首尾空格和 Markdown SQL 代码块。
2. 使用 sqlglot.parse(cleaned, read="duckdb") 解析。
3. 必须恰好只有一条语句。
4. 根节点必须是 SELECT 或 WITH 查询。
5. 禁止 INSERT、UPDATE、DELETE、MERGE、CREATE、DROP、ALTER、COPY、ATTACH、DETACH、事务和权限管理节点。
6. 禁止 SELECT *，要求显式列出投影字段。
7. 数据库必须在 AccessScope 中允许。
8. 表名必须是合法的白名单表名。
9. 禁止跨库引用、catalog 访问和文件函数。
10. 如果有表级权限，引用的每张表都必须通过 allows_table()。

为什么要禁用 SELECT *：

- 防止返回不必要的 JD、证据或内部字段。
- 让模型明确选择业务字段，减少结果结构漂移。
- 方便前端表格、图表和评测比较。
- 避免数据表新增字段后，历史 SQL 的输出契约突然变化。

### 6.3 connect() 的外部访问边界

DuckDB 连接会把 CSV 文件注册成视图，然后设置：

    SET allowed_paths = ?;
    SET enable_external_access = false;

其意图是：

- 允许引擎在受控阶段读取已登记的 CSV 文件。
- 用户 SQL 执行阶段禁止任意文件系统访问。
- 用户只能查询应用注册的 CSV 视图，而不能使用 read_csv()、read_text() 等函数读取其它路径。

这也是为什么安全不能只靠 Prompt。Prompt 中写了“不要读文件”不等于数据库执行器真的阻止了文件读取。

### 6.4 校验错误和执行错误的区别

| 阶段 | 示例 | validation | 是否执行 |
|---|---|---|---|
| 解析 | SQL 少了括号 | rejected | 否 |
| 只读规则 | DELETE FROM jobs | rejected | 否 |
| 表白名单 | SELECT x FROM secret_table | rejected | 否 |
| 访问控制 | 用户无权访问某表 | rejected | 否 |
| 字段绑定 | SELECT salary_min FROM jobs | passed 后由 DuckDB 发现错误 | 是，随后失败 |
| 数据读取 | CSV 类型转换或数据库错误 | passed | 是，随后失败 |

未知字段往往要等到 DuckDB 绑定阶段才能发现，所以自修正环既处理校验失败，也处理执行失败。

## 7. SQL Self-Correction：有限、可解释的自修正

### 7.1 为什么要修复，为什么不能无限修复

完全 fail-fast 会让一个可修复的小错误直接暴露给用户；无限重试则会带来：

- 成本失控；
- 延迟不可预测；
- 同一个错误被模型反复放大；
- 模型可能尝试绕过安全策略；
- 日志难以解释最终使用了哪条 SQL。

阶段二选择固定上限：

    MAX_ATTEMPTS = 3

也就是一次首轮生成加最多两次修复。max_attempts 构造参数可以设为 1、2 或 3，但不能超过 3。

### 7.2 错误分类

classify_sql_error() 将异常或错误文本映射到有限枚举：

    def classify_sql_error(
        error: str | BaseException | None,
    ) -> tuple[SqlErrorKind, bool]:

返回值是：

    (error_kind, retryable)

当前可修复矩阵：

| 错误 | 示例 | 是否回喂模型 | 原因 |
|---|---|---:|---|
| syntax | 括号、关键字或解析错误 | 是 | 模型通常可以修正语法 |
| unknown_field | 列名写错 | 是 | 完整 Schema 可帮助替换字段 |
| unknown_table | 表名写错 | 是 | 白名单 Schema 可帮助修正 |
| type_binding | 类型不能比较或转换 | 是 | 可以调整 SQL 表达式 |
| permission | 无权访问数据库/表 | 否 | 不能让模型绕过权限 |
| security | 写操作、SELECT *、文件函数 | 否 | 这是策略违规，不是普通 SQL 拼写错误 |
| database_not_found | 数据库目录不存在 | 否 | 需要资源/配置处理 |
| timeout | 执行超时 | 否 | 需要查询优化或任务级重试策略 |
| empty_result | 无结果语义 | 否 | 不能靠换 SQL 擅自改变用户口径 |
| model_unavailable | 模型调用失败 | 否 | SQL 修复也依赖同一个不可用模型 |
| unknown | 未知异常 | 否 | 先保守停止，避免误重试 |

bounded_error() 会压缩连续空白并限制长度：

    def bounded_error(
        error: str | BaseException | None,
        limit: int = 1200,
    ) -> str:
        message = re.sub(r"\s+", " ", str(error or "")).strip()
        return message[:limit]

它的作用是同时控制：

- Prompt 注入的错误体积；
- SSE 事件和任务快照大小；
- 日志中异常文本的扩散；
- 通过错误消息回显过多内部路径的风险。

### 7.3 修复上下文的结构

可修复错误不会把完整异常对象传给模型，而是构造有限字典：

    {
        "attempt": attempt,
        "failed_sql": sql,
        "error_kind": kind.value,
        "error": bounded_error(error),
    }

下一次生成时，用户载荷会变成：

    {
        "query": plan.query,
        "repair": {
            "failed_sql": previous["failed_sql"],
            "error_kind": previous["error_kind"],
            "error": previous["error"],
            "attempt": previous["attempt"],
        },
        "instruction": "只修正导致错误的 SQL，保持用户问题和结果口径不变。",
    }

这句话非常关键：修复应该改变导致错误的部分，不应该趁机改变用户的问题、过滤条件、统计口径或输出字段。

### 7.4 修复流程示意

    for attempt_number in range(1, self.max_attempts + 1):
        generated = self._generate(plan, catalog, previous)
        sql = generated.sql

        try:
            safe_sql = engine.validate_sql(database, sql, scope)
        except Exception as exc:
            kind, retryable = classify_sql_error(exc)
            attempts.append(rejected_attempt(...))
            if not retryable or attempt_number >= self.max_attempts:
                return failed_result(...)
            previous = repair_context(sql, kind, exc, attempt_number)
            emit("query.sql_repair", previous)
            continue

        execution = engine.execute(database, safe_sql, scope)
        if execution.success:
            return completed_result(...)

        kind, retryable = execution_error(execution)
        attempts.append(executed_but_failed_attempt(...))
        if not retryable or attempt_number >= self.max_attempts:
            return failed_result(...)
        previous = repair_context(safe_sql, kind, execution.error, attempt_number)
        emit("query.sql_repair", previous)

这个循环有三个必须同时满足的停止条件：

1. 执行成功；
2. 错误不可修复；
3. 尝试次数达到上限。

### 7.5 具体例子：未知字段可以修复

模型第一次生成：

    SELECT missing_column FROM jobs

DuckDB 返回未知字段错误，记录：

    {
      "attempt": 1,
      "validation": "passed",
      "execution": "failed",
      "error_kind": "unknown_field",
      "retryable": true
    }

模型第二次生成：

    SELECT job_id FROM jobs LIMIT 1

执行成功后，结果中保留两次 attempt。用户可以知道最终 SQL 不是首轮生成的，也可以在评测中计算“首轮失败、纠错后成功”的恢复率。

### 7.6 具体例子：安全错误不能修复

模型生成：

    SELECT * FROM jobs

DuckDbEngine.validate_sql() 返回安全错误。QueryAgent 记录一次：

    {
      "attempt": 1,
      "validation": "rejected",
      "execution": "failed",
      "error_kind": "security",
      "retryable": false
    }

即使模型理论上能够改成显式字段，当前策略也不把安全策略错误交给模型绕过。更稳妥的生产设计是让生成 Prompt 和模型评测减少这类错误，同时把策略违规保留为可观测的失败。

## 8. Query 事件与工作流接入

### 8.1 QueryAgent 的事件接口

QueryAgent 不直接依赖 FastAPI SSE 实现，而是接收一个可选的 event_sink：

    def _emit(
        sink: EventSink | None,
        event_type: QueryEventType | str,
        payload: dict[str, Any],
    ) -> None:
        if sink:
            sink(str(event_type), payload)

这种依赖倒置有几个好处：

- QueryAgent 可以被同步测试、CLI 或 LangGraph 调用。
- SSE、JSONL、内存事件列表可以分别实现 sink。
- Agent 不需要知道 task_id、sequence 或 HTTP 连接细节。
- 事件和任务存储可以在更上层统一加 event_id、task_id 和递增序号。

阶段 0 的 SseEvent 是跨请求协议，阶段二的 Query 事件是 QueryAgent 的领域事件。工作流层负责把后者汇入统一执行轨迹。

### 8.2 当前发出的事件和 payload

| 事件 | 典型 payload |
|---|---|
| query.schema_loaded | database、dataset_version、table_count、field_count、token 统计 |
| query.sql_generated | attempt、sql、explanation |
| query.sql_validated | attempt、validation、error_kind、retryable |
| query.sql_executed | attempt、execution、row_count 或错误摘要 |
| query.sql_repair | failed_sql、error_kind、bounded error、attempt |
| query.completed | attempts、row_count、dataset_version |
| query.failed | attempts、error_kind、错误摘要 |

事件中包含 SQL 是为了可解释性和调试；错误通过 bounded_error() 限长；事件不包含模型隐藏推理内容。

### 8.3 _query_agent() 如何接入 LangGraph

工作流中的节点会创建列表型事件收集器：

    execution_log: list[dict[str, Any]] = []

    def on_event(event_type: str, payload: dict[str, Any]) -> None:
        execution_log.append({
            "stage": event_type,
            "success": event_type != "query.failed",
            **payload,
        })

然后调用：

    result = self.query_agent.run(
        state["standalone_query"] or state["query"],
        database,
        access_scope=state.get("access_scope") or {},
        event_sink=on_event,
    )

成功时，工作流把以下信息放入 QueryResult：

- sql
- columns
- rows
- sql_attempts
- dataset_version
- prompt_token_count
- execution_log
- workflow_mode = full_schema_query_agent

失败时也保留 sql_attempts 和 execution_log，而不是只返回一句“查询失败”。

### 8.4 当前实现和完整 SSE 设计的区别

设计文档希望最终的事件具备：

- event_id
- task_id
- 递增 sequence
- 时间戳
- Pydantic payload
- append-only JSONL 持久化
- 断线重连和重复事件去重

阶段二当前已经完成 QueryAgent 的领域事件和工作流汇流，但完整的任务 API、事件持久化和断线恢复属于运行时基础设施的后续集成。学习时要区分：

    QueryAgent event_sink
        = Agent 级事件回调

    SseEvent / Runtime Store
        = 跨请求、可恢复的统一传输和持久化协议

这两个层次不能混为一谈。

## 9. Coordinator：意图路由、资源检查和澄清

### 9.1 Coordinator 的职责边界

Coordinator 的类注释直接表达了边界：

    class Coordinator:
        """只做路由、资源/新鲜度检查和澄清，不执行 scraper 或 SQL。"""

它不是“什么都能做的总 Agent”。具体职责是：

- 解析岗位关键词和城市；
- 判断是否需要简历；
- 检查对应岗位数据集是否存在；
- 检查最近成功采集是否过期；
- 返回 clarify、request_crawl 或原始动作；
- 把结构化决定交回工作流。

### 9.2 parse_target()：从请求中提取目标岗位

    def parse_target(
        self,
        text: str,
        target: TargetJobRequest | None = None,
    ) -> TargetJobRequest | None:

参数和规则：

- 如果已经有经过校验的 target，直接返回，不重新猜测。
- 从固定城市集合中查找城市。
- 移除“请帮我、查询、统计、岗位、薪资”等常见噪声词。
- 用标点截断多余说明。
- 识别有限的经验和学历枚举。
- 没有可用关键词时返回 None。

当前城市列表包括北京、上海、广州、深圳、杭州、南京、苏州、成都、武汉、西安、重庆、天津、厦门、长沙、合肥和宁波。

这里的实现是一个确定性的轻量解析器，不是试图用规则覆盖所有中文表达。遇到不明确的文本，Coordinator 应返回澄清，而不是静默猜测一个城市或岗位。

### 9.3 inspect_dataset()：为什么检查 crawl_runs.csv

    def inspect_dataset(
        self,
        target: TargetJobRequest,
        *,
        now: datetime | None = None,
    ) -> DatasetAvailability:

它检查：

1. crawl_runs.csv 是否存在；
2. status == succeeded；
3. keyword 与目标关键词不区分大小写匹配；
4. 如果目标有城市，则城市精确匹配；
5. dataset_version 不为空；
6. 选择 finished_at 或 started_at 最新的一次成功批次；
7. 计算数据年龄是否不超过 freshness_days，默认 7 天。

为什么不用：

    SELECT MAX(scraped_at) FROM jobs

因为岗位行的最大时间戳不能证明一次采集完整成功。采集可能被风控中止、详情页部分失败或 ETL 没有发布；crawl_runs.csv 是批次级状态和版本发布的证据。

dataset_root 可以传：

- .../data/databases
- .../data/databases/jobs_market

方法会根据目录名决定是否追加 jobs_market。

### 9.4 decide()：资源门控和路由结果

    def decide(
        self,
        request: UserRequest,
        *,
        action: str,
        now: datetime | None = None,
    ) -> RouteDecision:

典型决策顺序：

    direct_response / data_qa
        → 直接返回，不检查岗位数据

    其它动作
        → 解析 TargetJobRequest
        → 无关键词：clarify(target)
        → 无城市：clarify(city)
        → career_advice 且无 resume_id：clarify(resume_id)
        → 检查 crawl_runs.csv
        → 无匹配或数据过期：request_crawl
        → 有新鲜已发布数据：返回 database_query 或 career_advice

城市缺失时的澄清选项是结构化列表，而不是一段只能人工解析的文本：

    CoordinatorClarification(
        parameter="city",
        question="请选择目标城市。",
        reason="城市会改变岗位样本和薪资统计结果。",
        options=self.DEFAULT_CITY_OPTIONS,
    )

这对前端很重要：前端可以直接渲染选择项，用户选择后再恢复任务。

### 9.5 career_advice 的阶段二边界

当前阶段已经完成：

- career_advice 意图枚举；
- 目标岗位和城市解析；
- resume_id 缺失澄清；
- 岗位数据集存在性和新鲜度检查；
- request_crawl 等待结果；
- 工作流中的 career clarification 状态。

但真正的 CareerAgent——包括简历文本解析、PII 脱敏、JD 技能结构化抽取、技能别名归一化、证据覆盖/缺口分析和报告拼装——属于后续阶段。阶段二的 Coordinator 只负责把输入资源准备好，不能把“已经能路由”描述成“已经完成职业建议”。

## 10. ChartSpec 与确定性 ECharts 映射

### 10.1 为什么不让模型直接生成 ECharts option

任意 ECharts option 可能包含：

- 未知字段；
- 大量不可控配置；
- JavaScript 回调或事件；
- 与前端版本不兼容的结构；
- 超出产品允许范围的视觉和交互。

因此模型只输出业务级 ChartSpec，后端通过 chart_spec_to_echarts() 生成确定性 option。

### 10.2 函数签名和输入验证

    def chart_spec_to_echarts(
        spec: ChartSpec | Mapping[str, Any],
        rows: Sequence[Mapping[str, Any]],
    ) -> dict[str, Any]:

参数：

| 参数 | 说明 |
|---|---|
| spec | 已校验的 ChartSpec 或可由 Pydantic 校验的字典 |
| rows | 查询结果行；每行是字段名到值的映射 |
| 返回值 | ECharts option 字典 |

如果传入普通映射，会先执行：

    chart = ChartSpec.model_validate(spec)

如果查询行缺少 category_field 或 value_field，bar/line/pie 会直接抛出字段错误。数值字段通过 _number() 转换，无法转换的值变成 None，不会执行任意表达式。

### 10.3 bar、line、pie

bar 和 line 共用分类轴：

    {
        "title": {"text": chart.title},
        "tooltip": {"trigger": "axis"},
        "xAxis": {"type": "category", "data": categories},
        "yAxis": {"type": "value"},
        "series": [{
            "type": "line" if chart.type == "line" else "bar",
            "data": values,
            "smooth": False,
        }],
    }

max_items 会限制类别和值的数量，当前默认 12，允许 3～30。这样可以避免用户一次查询返回几百个类别，把图表变成不可读的长列表。

pie 使用：

    {
        "title": {"text": chart.title},
        "tooltip": {"trigger": "item"},
        "series": [{
            "type": "pie",
            "data": [
                {"name": category, "value": value}
                for category, value in zip(categories, values)
            ],
        }],
    }

### 10.4 histogram 的分桶

直方图只需要 value_field 的数值：

    values = [
        number
        for row in rows
        if chart.value_field in row
        for number in [_number(row[chart.value_field])]
        if number is not None
    ]

如果没有可用数字，函数抛出错误。最小值和最大值不同的情况下：

    width = (high - low) / chart.bins
    counts = [0] * chart.bins

    for value in values:
        index = min(chart.bins - 1, int((value - low) / width))
        counts[index] += 1

min(chart.bins - 1, ...) 是边界保护，保证最大值落入最后一个桶，而不是生成越界索引。bins 由 Pydantic 限制在 3～50，避免空桶过少或配置失控。

### 10.5 确定性映射的好处

- 同样的 ChartSpec 和查询结果得到同样的 option。
- 测试可以直接断言 series[0]["type"] 和数据。
- 前端不需要信任模型生成 JavaScript。
- 图表语义、字段和数据来源可追踪到 source_task_id。
- 后续替换 ECharts 或增加其它渲染器时，业务契约不变。

## 12. 可靠性、安全边界和可观测性

### 12.1 防御性解析

阶段二对模型和外部文件都不做“默认可信”处理：

- 模型返回值先检查是不是字典。
- SqlGeneration.model_validate() 校验 SQL 字段和长度。
- QueryPlan 拒绝空查询。
- ChartSpec 限制图表类型、项目数量和 bins。
- AccessScope 在 Schema 构造、SQL 校验和执行层重复使用。
- Schema 文件不存在、版本不完整或 CSV 不一致时显式失败。

### 12.2 错误信息有界

错误信息不能原样无限传播到：

- Prompt；
- SSE；
- append-only 日志；
- 任务快照；
- 前端结果。

bounded_error() 统一限长和空白折叠，既保留排查线索，也避免把内部路径、连接细节或巨型异常堆栈扩散给用户。

### 12.3 权限不是 Prompt 约定

即使系统提示写着“只能查询 jobs”，也必须在代码层检查：

- SchemaCatalogBuilder 不向模型展示无权表。
- DuckDbEngine.validate_sql() 检查数据库和表权限。
- execute() 再次校验，避免调用方绕过 QueryAgent。
- 权限错误被标记为不可修复。

这是“策略执行点”和“模型建议点”的区别：

    Prompt：告诉模型应该怎么做
    Validator/Executor：强制系统不能做什么

### 12.4 可观测性和结果可解释性

SqlAttempt、dataset_version、prompt_token_count 和 execution_log 让一次结果可以回答：

- 这次查的是哪个数据集版本？
- Prompt 大约用了多少 token？
- 首轮 SQL 是否失败？
- 失败是什么类型？
- 修复了几次？
- 最终 SQL 是否通过安全校验？
- 查询返回多少行？
- 前端应该展示哪个阶段事件？

这比只保存最终自然语言答案更适合调试和面试答辩。

## 13. 实现边界与后续阶段

### 13.1 旧 Schema 检索路径仍存在的原因

设计文档目标是移除 Schema RAG；当前工作流对 jobs_market 的主路径已经使用完整 Schema Catalog：

    if allowed == {"jobs_market"}:
        return "query_agent"
    return "retrieve_schema"

旧 retrieve_schema 分支仍为非 jobs_market 或旧 AskData 示例保留，原因是：

- 仓库中已有旧数据库查询行为和测试；
- 阶段二先替换目标业务主路径，减少一次性破坏兼容性的风险；
- 旧路径不是 jobs_market QueryAgent 的 Schema 供给方式。

因此正确的表述是：

> 阶段二的 jobs_market QueryAgent 主链路已移除 Schema RAG 依赖；旧 AskData 兼容路径仍保留，后续可以在兼容迁移完成后清理。

不能简单说“整个仓库所有 Schema 检索代码都已经删除”。

### 13.2 CareerAgent 尚未完成

当前 Coordinator 可以把 career_advice 任务送到：

- 关键词和城市澄清；
- 简历 resume_id 澄清；
- 岗位数据集检查；
- request_crawl 等待状态；
- 数据资源可用后的下一步。

但以下能力仍属于后续阶段：

- 简历文本抽取；
- PII 脱敏；
- JD 技能结构化抽取；
- 技能别名归一化；
- JD 证据和简历证据匹配；
- covered/partial/missing 分析；
- STAR 改写和面试清单。

面试时应该主动说明这个边界，因为“有 career_advice 路由”不等于“职业建议 Agent 已全部实现”。

### 13.3 token 统计仍是估算

当前 ceil(chars / 4) 是工程上的可复现估算，不同模型 tokenizer 的真实 token 数会不同。后续可以：

1. 按实际部署模型接入对应 tokenizer；
2. 记录输入和输出 token；
3. 在评测中记录成本；
4. 比较完整 Schema、分层 Schema 和检索 Schema 的准确率、延迟、成本。

### 13.4 SQL 错误分类的演进方向

当前错误分类依赖稳定的关键词映射。更严格的生产版本可以：

- 对 sqlglot 异常、DuckDB 异常和权限异常使用具体异常类型；
- 给每类错误定义结构化错误码；
- 增加错误分类回归样本；
- 避免把某个数据库版本新增的错误文本误判为可重试；
- 把“空结果”作为业务语义处理，而不是 SQL 语法修复。

### 13.5 评测还应继续扩展

阶段二专项测试证明了流程边界，但不等于 NL2SQL 语义准确率已经达标。后续评测应加入：

- 至少 50 道中文问题；
- golden SQL 或可比较结果；
- P50/P75 薪资；
- 技能频率；
- 经验和学历交叉；
- 多条件联合过滤；
- 首轮准确率；
- 修复后准确率；
- Self-Correction 恢复率；
- 平均尝试次数和 P95 延迟；
- token 和成本；
- 纠错开关消融实验。

## 14. 模拟面试问答

### Q1：阶段二主要解决什么问题？

**答：** 阶段一把岗位数据变成了可查询的版本化 CSV，但用户还不能可靠地用自然语言访问它。阶段二实现了从自然语言到 SQL 结果的完整闭环：Coordinator 做路由和资源检查，QueryAgent 读取权限过滤后的完整 Schema，模型生成结构化 SQL，DuckDB/sqlglot 做只读安全校验，执行失败时对限定错误进行最多两次修复，并把过程以结构化事件返回前端。

### Q2：为什么没有继续使用 Schema RAG？

**答：** 当前 jobs_market 只有 4 张表、66 个字段，完整 Schema 的上下文规模可测量且可接受。全量注入省去了 embedding、rerank、索引一致性和额外网络调用，也能完整保留表关系。我们没有把这个取舍泛化到所有规模，而是记录了 Prompt 字符数和可复现的 token 估算；未来如果 Schema 规模增大，会通过准确率、延迟和成本评测决定是否引入分层或检索。

### Q3：完整 Schema 注入会不会把敏感数据直接送给模型？

**答：** Builder 先根据 AccessScope 过滤数据库、表和关系，再渲染 Prompt。字段本身仍然可以出现，因为模型需要知道可查询的结构；但 jd_text、evidence_text、job_link、company、title 等字段不注入样例值，也不会把完整 JD 文本放进 Schema Prompt。真正的访问控制仍在 SQL 校验和执行层，不能只依赖 Prompt。

### Q4：prompt_token_count 是精确值吗？

**答：** 当前不是供应商 tokenizer 的精确值，而是 ceil(len(rendered_schema) / 4) 的可复现估算。项目明确同时记录字符数和估算 token 数，避免把近似值误报为精确成本。部署到固定模型后可以接入对应 tokenizer 做真实统计。

### Q5：模型输出已经用了结构化 JSON，为什么还要 SQL 校验？

**答：** 结构化输出只保证外形，例如有一个 sql 字段；它不能保证 SQL 存在、只读、未越权或业务语义正确。模型仍可能输出 DELETE、SELECT *、未知表、文件函数和跨库引用。因此必须在模型之外用 sqlglot 解析、节点白名单、表白名单、权限检查和 DuckDB 只读连接强制执行。

### Q6：为什么禁止 SELECT *？

**答：** 一是避免返回不必要的 JD、证据或内部字段；二是表新增字段时，历史查询的输出结构不会悄悄变化；三是显式字段更容易做图表、前端表格和评测；四是可以让模型明确表达查询需要的数据，而不是把整张表暴露出来。

### Q7：哪些错误会触发 SQL Self-Correction？

**答：** 当前只有语法错误、未知字段、未知表和类型绑定错误可重试。权限错误、安全策略错误、数据库不存在、超时、空结果、模型不可用和未知错误都不交给模型绕过。修复逻辑使用 SqlErrorKind 和 retryable，而不是根据“所有异常都试一次”的宽泛规则。

### Q8：为什么安全错误不能让模型自行修复？

**答：** 安全错误代表系统策略被触发，例如写操作、SELECT *、文件函数、跨库访问或权限不足。把这类错误回喂模型可能诱导模型寻找绕过方式，也会把策略违规混同为普通拼写错误。安全策略应该由确定性代码执行；模型可以在下一次正常生成中减少违规，但不能作为权限守卫的决策者。

### Q9：为什么最多三次尝试？

**答：** 三次包括首轮生成和最多两次修复，和设计文档一致。上限可以控制模型成本、响应延迟和错误放大；每次尝试都保存在 SqlAttempt 中，最终结果可解释。SqlAttempt.attempt <= 3 和 QueryAgent.MAX_ATTEMPTS 同时约束数据和执行循环，避免某个调用方突破上限。

### Q10：如果第三次仍然失败，系统做什么？

**答：** 记录第三次 SqlAttempt，如果错误可修复但已经耗尽次数，则返回 status = failed、错误类别和有界错误摘要；不会继续向模型发送第四次请求，也不会偷偷执行未经验证的 SQL。这个“纠错耗尽后的 fail-fast”是设计的一部分。

### Q11：未知字段是在 SQL 校验阶段发现的吗？

**答：** 不一定。sqlglot 可以发现语法和结构问题，DuckDB 的绑定阶段通常才会发现某个列名不存在。因此 QueryAgent 既处理 validate_sql() 抛出的错误，也处理 execute() 返回的失败，并统一转换为 SqlErrorKind。

### Q12：如何避免 QueryAgent 阻塞异步服务？

**答：** 当前 DuckDB 和模型客户端仍有同步接口，因此提供 async def arun()，内部用 asyncio.to_thread(self.run, ...) 把同步闭环移出事件循环。它是兼容层；如果模型 SDK 原生提供异步调用，后续可以把生成步骤进一步改成真正的 async I/O。

### Q13：Coordinator 和 QueryAgent 的职责有什么区别？

**答：** Coordinator 决定“现在应该做什么以及资源是否准备好”，例如解析城市、检查简历和 crawl_runs.csv、返回澄清或请求采集。QueryAgent 决定“在资源准备好后，如何安全地把一个查询变成 SQL 并执行”。Coordinator 不写 SQL，QueryAgent 不运行爬虫，这样每个 Agent 的权限边界清晰。

### Q14：为什么用 crawl_runs.csv 判断数据新鲜度，而不是看岗位表的最新时间？

**答：** 岗位行的最大时间戳只能说明某一行是什么时间抓到，不能证明该批次成功完成或已发布。如果采集被风控中止、详情页部分失败或 ETL 没有原子发布，单看 MAX(scraped_at) 会产生假新鲜度。crawl_runs.csv 记录了关键词、城市、状态、完成时间和 dataset_version，更适合做资源门控。

### Q15：城市缺失时为什么不自动猜一个默认城市？

**答：** 城市会直接改变岗位样本、薪资分布和技能频率。模糊文本下静默选择城市会制造看似合理但不可解释的统计结果。当前实现返回结构化 clarify(city)，并提供固定城市选项，让用户明确选择后恢复任务。

### Q16：阶段二为什么已经增加 career_advice 路由，但没有职业报告？

**答：** 阶段二先完成资源门控和编排边界：目标岗位、城市、简历和数据集版本必须明确且可用。真正的 CareerAgent 属于后续阶段，负责简历解析、JD 技能抽取、证据覆盖分析和报告生成。提前接入路由可以固定输入输出契约，但不会假装后续分析已经完成。

### Q17：为什么图表要用 ChartSpec，而不是让 LLM 直接写 ECharts option？

**答：** ChartSpec 只允许四种图表类型和有限字段，后端根据它生成确定性 option。这样可以验证字段、限制项目数量和 bins，禁止任意脚本与未授权配置，保证同样的查询结果得到同样的图表。模型负责选择业务语义，程序负责渲染细节。

### Q18：直方图分桶如何避免最大值越界？

**答：** 桶宽是 (high - low) / bins，索引是 int((value - low) / width)，最后使用 min(bins - 1, index) 把最大值钳制到最后一个桶。bins 又由 Pydantic 限制在 3～50，避免产生空桶过少或配置失控。

### Q19：SSE 事件和模型思维链有什么区别？

**答：** SSE 事件是经过契约约束的执行状态，例如 Schema 已加载、SQL 已生成、校验通过、修复一次或返回多少行；它不暴露模型的隐藏推理过程。QueryAgent 通过 event_sink 发布领域事件，工作流再将其汇入统一的 SseEvent/Runtime Store。这样用户能理解系统进展，同时不会把内部推理当成产品协议。

### Q20：如何测试 Self-Correction，而不依赖真实 LLM？

**答：** QueryAgent 构造函数接受可选 sql_generator，测试使用 FakeModel 按固定顺序返回 SQL。这样可以确定性地验证未知字段修复成功、安全错误不重试、三次上限和事件数量。真实模型调用应放在单独的 E2E 或评测任务中，单元测试不应依赖外部服务和随机输出。

### Q21：阶段二当前最大的技术风险是什么？

**答：** 第一，SQL 错误分类目前主要依赖异常文本关键词，需要持续补充不同 DuckDB/sqlglot 版本的回归样本。第二，token 统计是字符数估算，还没有接入部署模型 tokenizer。第三，当前工作流保留旧 AskData 检索兼容分支，迁移完成后需要清理或统一。第四，NL2SQL 的专项测试验证了安全和控制流，但还不能替代 50+ 题的语义准确率评测。

### Q22：如果让你继续改进阶段二，你会怎么做？

**答：** 我会按风险优先级做四件事：

1. 使用具体异常类型和结构化错误码替代部分文本匹配。
2. 接入实际模型 tokenizer 和成本记录，比较全量 Schema 与分层 Schema。
3. 完善统一 SSE Runtime Store 的事件序号、断线恢复和重复去重。
4. 建立独立 eval_dev/eval_test NL2SQL 数据集，分别评估首轮准确率、修复恢复率、延迟和成本，避免只用功能测试证明语义效果。

## 16. 简历和面试中的项目表达

### 16.1 一句话版本

> 在 OfferAgent 中实现了基于 Pydantic 契约和 DuckDB 只读执行器的 NL2SQL QueryAgent：将版本化岗位 Schema 全量注入 Prompt，使用 sqlglot 做安全校验，并对语法、字段、表和类型错误进行最多两次有界 SQL 自修正，同时通过 Coordinator 完成岗位城市、简历和数据新鲜度的资源门控。

### 16.2 30 秒版本

> 阶段一已经把 BOSS 岗位数据 ETL 成版本化 CSV 和 Schema。阶段二我没有继续引入 Schema RAG，而是基于当前 4 张表、66 个字段构造完整 Schema Catalog，并记录 Prompt 字符数和 token 估算。QueryAgent 生成结构化 SQL 后，先通过 sqlglot 和 DuckDB 只读校验，再执行查询；只有语法、未知字段、未知表和类型绑定错误会进入修复环，最多三次尝试，权限和安全错误直接停止。Coordinator 负责城市、简历和 crawl_runs 新鲜度检查，所有 SQL 生成、校验、执行和修复都通过结构化事件返回。

### 16.3 60 秒版本

> 这个阶段主要解决“模型如何安全地查询岗位市场数据”以及“求职任务在资源不足时如何澄清”的问题。首先，我在 Pydantic 中定义了 QueryPlan、SchemaCatalog、SqlAttempt、QueryAgentResult 和错误/事件枚举，避免跨 Agent 传递无约束字典。Schema Builder 从阶段一发布的 schema 读取物理表名、字段类型、中文含义、别名、聚合和关系，并依据 AccessScope 过滤后整体注入 Prompt。QueryAgent 的运行顺序是生成结构化 SQL、校验单语句/只读/表白名单/权限、执行 DuckDB CSV 视图，失败时仅对四类 SQL 错误做有界修复，最多两次，所有尝试都有记录。Coordinator 独立负责岗位关键词和城市解析、resume_id 检查以及按 crawl_runs 和 dataset version 判断数据是否新鲜。图表由受限 ChartSpec 确定性映射为 ECharts，模型不能直接输出任意前端配置。当前边界是 CareerAgent 的简历证据分析和完整 SSE 持久化仍属于后续工作。

### 16.4 面试回答的底线

不要声称：

- “使用 tokenizer 精确统计了所有 token”，当前是字符数除以 4 的估算。
- “整个仓库的 Schema RAG 已经删除”，当前保留了旧 AskData 兼容分支。
- “CareerAgent 已完成”，当前完成的是 career_advice 的资源门控和路由。
- “SQL 一定正确”，当前实现的是安全校验、有限修复和可观测失败。
- “测试覆盖了真实模型的语义准确率”，当前专项测试主要验证控制流、安全边界和契约；语义评测仍需要独立的 50+ 题基准。

能够主动说明这些边界，通常比只罗列功能更能体现对 Agent 工程可靠性的理解。
