## 一、项目背景与本轮对话结论

OfferAgent 的目标是构建一个面向求职决策的 Multi-Agent 系统，主链路可以概括为：

1. 通过 BOSS 直聘 CDP 被动捕获采集目标岗位；
2. 经过 ETL、清洗和数值化，将岗位数据写入 DuckDB；
3. 通过 NL2SQL 让用户用自然语言查询岗位市场数据；
4. 使用 SQL 自修正、技能缺口分析、简历证据和职业建议生成决策报告；
5. 通过 SSE 向前端展示结构化执行轨迹、进度、SQL、图表和报告。

在开始真正接入所有 Agent、真实采集和 LLM 之前，项目需要先回答几个工程问题：

- 用户请求的输入格式是什么？
- 一个长任务有哪些稳定的生命周期状态？
- 任务失败应该如何分类和返回？
- 前端通过什么格式接收进度？
- SSE 断线后如何从上次位置恢复？
- 任务状态和事件如何跨 HTTP 请求保存？
- 阻塞型采集器或同步模型调用如何避免卡住 FastAPI 事件循环？
- 后端、测试和 BOSS 集成能否使用同一个 Python 环境启动？

因此设计文档把阶段 0 放在最高优先级，并把它定义为“工程契约与流式 Spike”。本阶段不追求完成最终业务价值，而是先把后续所有模块必须依赖的边界、状态和运行基础固定下来。

本轮对话还确认了 Python 环境的统一方案：

- 根目录只保留一个 Python 项目配置文件，也就是根目录的 pyproject.toml；
- 根目录只保留一个 uv.lock，并使用 Python 3.11；
- backend 和 integrations/boss_zhipin 作为源码目录运行，不再各自维护独立的 pyproject.toml 和 uv.lock；
- 前端继续使用 frontend/package.json 和 frontend/package-lock.json，因为 Vue/Vite 属于 Node 生态，不能伪装成 Python 依赖；
- uv 负责后端、测试和 BOSS 集成，npm 负责前端；
- 统一环境的意义是让测试、后端和集成脚本不依赖进入某个子目录后再单独同步环境。

这个环境决策与阶段 0 有直接关系：契约测试、Runtime Store 测试、SSE 测试和真实集成脚本需要共享同一套 Python 依赖，否则“能在某个子项目运行”不能说明整个仓库的工程契约是可复现的。

## 二、阶段 0 技术栈介绍

阶段 0 的技术选择围绕五个问题展开：如何约束跨模块数据、如何执行异步长任务、如何把进度推送给前端、如何保存任务状态、如何让环境和测试可复现。

### 2.1 Pydantic：运行时数据契约

Pydantic 是基于 Python 类型标注进行运行时数据校验和序列化的库。本项目用它定义 UserRequest、TargetJobRequest、TaskSnapshot、SseEvent、FailureInfo 等模型。

它主要解决外部数据不可信的问题：

- 前端请求可能缺字段、类型错误或拼写错误；
- scraper 返回的数据可能不完整；
- LLM 输出可能不是预期结构；
- 不同 Agent 可能对同一个字段产生不同约定。

Pydantic 可以校验字段类型、枚举值、空值和自定义规则，也可以使用 extra="forbid" 拒绝未声明字段。它保证的是结构和边界，不代表业务事实一定正确；例如它可以验证 city 是字符串，但不能证明这个城市确实存在。

### 2.2 FastAPI：HTTP API 与异步边界

FastAPI 是基于 Python 类型标注的异步 Web 框架。阶段 0 使用它提供任务创建、任务查询和 SSE 事件订阅接口。

FastAPI 会根据路由参数中的 Pydantic 模型自动解析 JSON 请求体并返回校验错误。阶段 0 的关键设计是：路由只负责接收请求、创建任务、读取状态和发送事件；阻塞型 scraper、同步模型调用和长时间 ETL 不应直接运行在 HTTP handler 中。

### 2.3 SSE：Server-Sent Events 服务端推送

SSE 的全称是 Server-Sent Events，是一种基于 HTTP 的服务端到客户端单向事件流协议。浏览器可以通过 EventSource 连接服务端，服务端持续发送 id、event 和 data 字段。

SSE 适合本项目，因为前端主要需要接收任务进度，不需要与后端建立双向实时通道。它有浏览器原生支持、协议简单和可使用 Last-Event-ID 自动重连等优点。

阶段 0 为事件增加 event_id、task_id、sequence、timestamp 和结构化 payload，使前端能够区分 task.started、step.completed、heartbeat 和 task.completed。SSE 只负责传输已经产生的事件，不负责任务调度、持久化或重试。

### 2.4 asyncio：异步执行与非阻塞等待

asyncio 是 Python 标准库中的异步 I/O 框架。阶段 0 使用 async def、await、asyncio.create_task 和 asyncio.sleep 模拟后台长任务。

asyncio.sleep 会把控制权交还给事件循环，time.sleep 或未经隔离的同步网络调用则可能阻塞整个 worker。asyncio.create_task 能把 coroutine 放到当前进程后台运行，因此适合 Spike；但它不提供进程重启后的恢复、跨进程调度和可靠重试，不能直接视为生产级任务队列。

### 2.5 Runtime Store：JSON 快照与 JSONL 事件日志

Runtime Store 是阶段 0 的轻量运行时存储：

- JSON 快照保存任务当前状态、sequence、result 或 error；
- append-only JSONL 保存任务经历过的事件；
- 快照适合快速查询“现在是什么”；
- 事件日志适合按 sequence 重放“发生过什么”。

快照写入使用临时文件、flush、fsync 和 os.replace，减少进程在写入中途退出时留下半个 JSON 的风险。事件写入检查 sequence 是否连续，并对相同 event_id 的重复事件执行幂等判断。

这种本地文件方案用于验证协议和恢复语义，不等价于生产数据库事务；多进程并发、跨机器共享、事件保留和任务恢复需要后续引入数据库或消息系统。

### 2.6 uv、Uvicorn 与测试工具

uv 负责统一 Python 环境和依赖锁定。阶段 0 的约定是根目录只有一个 pyproject.toml、一个 uv.lock，并通过 .python-version 固定 Python 3.11；backend、测试和 integrations/boss_zhipin 共享同一环境，前端仍由 npm 管理。

Uvicorn 是运行 FastAPI 的 ASGI 服务器。pytest 是测试框架，pytest-asyncio 支持异步测试，httpx 用于测试 API 和 SSE 相关行为。阶段 0 的测试关注完整行为，而不是只验证模块可以导入：包括契约校验、事件顺序、幂等、任务创建、heartbeat、SSE 和 Last-Event-ID 重连。

### 2.7 LangGraph、DuckDB、Vue/Vite 的阶段边界

LangGraph 是设计文档中计划用于组织 Coordinator、MarketDataAgent、QueryAgent 和 CareerAgent 的状态图框架；DuckDB 负责岗位数据分析；Vue/Vite 负责前端界面和事件展示。

它们属于项目整体技术栈，但阶段 0 不先实现全部业务。阶段 0 先固定这些组件未来接入所依赖的 UserRequest、TaskSnapshot 和 SseEvent。等真实 Agent、采集器和查询流程接入时，只需将具体步骤映射为统一事件，而不需要重新发明任务协议。

## 三、阶段 0 到底做什么

阶段 0 的完整任务可以分成六个主要部分，以及一个明确不阻塞本阶段的并行事项。

### 3.1 建立统一的仓库和运行边界

设计文档要求仓库形成清晰的 monorepo 结构，核心目录包括：

- backend：FastAPI、Agent、契约、运行时和测试；
- frontend：Vue/Vite 前端；
- integrations：BOSS 采集等外部系统集成；
- data：本地数据、fixture 或数据说明；
- eval：离线评测和回归数据；
- docs：设计文档和学习笔记。

阶段 0 还需要确定 Python 3.11、统一启动方式和统一测试入口。当前统一入口是：

~~~bash
uv lock
uv sync
uv run pytest
uv run python backend/run.py
~~~

前端仍然独立运行：

~~~bash
npm --prefix frontend ci
npm --prefix frontend run dev
~~~

### 3.2 定义 Pydantic 输入、输出和领域契约

阶段 0 要先定义后续模块共享的结构化对象，包括：

- UserRequest：用户提交的任务请求；
- TargetJobRequest：岗位搜索条件；
- TaskSnapshot：任务当前快照；
- SseEvent：对外发送的结构化事件；
- CrawlRunResult：采集运行结果；
- SqlAttempt：一次 SQL 生成、校验或执行尝试；
- CareerReport：职业分析报告；
- FailureInfo：可展示、可分类的失败信息。

这些对象不是简单的数据容器，而是模块之间的“工程合同”。合同一旦确定，API、LangGraph 节点、采集 worker、前端事件处理和测试都可以针对同一组字段开发。

### 3.3 固定状态和错误枚举

阶段 0 需要明确任务状态，例如：

- created：任务已创建，尚未开始执行；
- running：任务正在执行；
- waiting_clarification：需要用户补充信息；
- completed：任务成功完成；
- failed：任务失败；
- cancelled：任务被取消。

还需要定义采集状态和任务错误码。状态和错误码使用枚举而不是散落在代码中的字符串，避免一个模块使用 running、另一个模块使用 in_progress，最终导致前端和后端无法可靠协作。

### 3.4 固定异步边界

FastAPI 的 SSE endpoint 负责建立连接、读取事件和发送事件，不应该直接执行以下工作：

- 同步的 invoke；
- urllib 或 requests 等阻塞网络调用；
- 浏览器 CDP 操作；
- 长时间 ETL；
- 真实 scraper 主循环。

阶段 0 先用异步 fake executor 模拟长任务，将“创建任务”和“读取任务进度”与实际业务执行解耦。未来真实执行器可以是受控 worker、进程、任务队列或 LangGraph runtime，但前端不需要知道执行器的内部实现。

### 3.5 建立最小 SSE 事件协议

阶段 0 不要求完成所有 Agent 的真实流式输出，但必须验证以下核心能力：

- 创建任务后立即返回任务标识；
- 后台任务可以持续产生事件；
- SSE endpoint 能按顺序发送事件；
- 事件有稳定的 task_id、event_id 和 sequence；
- 客户端断线后可以使用 Last-Event-ID 恢复；
- 有心跳事件，避免长时间无数据时连接被代理误判为失活；
- 任务完成后可以通过普通 GET 查询最终快照。

### 3.6 建立 Runtime Store

阶段 0 使用本地文件做最小可恢复运行时存储：

- 任务快照写入 JSON；
- 事件写入 append-only JSONL；
- 运行时文件放在本地 data/local/runtime；
- 运行时目录不提交到 Git；
- 写快照时使用临时文件、flush、fsync 和原子替换；
- 事件 sequence 必须连续，重复 event_id 必须幂等或显式报错。

这个实现不是最终的分布式数据库方案，但它足以验证任务模型、事件协议和恢复语义。等契约稳定后，再根据部署形态替换成数据库、消息队列或专用事件存储。

### 3.7 真实采集是并行事项，不应阻塞阶段 0

设计文档特别强调：真实 BOSS 采集、登录态、风控和浏览器环境具有较高不确定性，不应成为契约和流式基础设施的前置阻塞条件。阶段 0 使用 fake flow 和 fixture 先证明任务系统能够工作，真实数据采集可以并行开发。

## 四、为什么必须有阶段 0

### 4.1 防止每个 Agent 自己发明一套协议

如果直接从 Coordinator、MarketDataAgent、QueryAgent 和 CareerAgent 开始开发，每个模块很容易自行定义：

- 不同的状态名；
- 不同的错误格式；
- 不同的进度字段；
- 不同的结果结构；
- 不同的重试语义。

短期看起来开发很快，长期会出现适配代码、分支判断和隐含约定。阶段 0 先把这些公共概念固定，后续 Agent 只需要实现自己的输入、输出和状态转换。

### 4.2 长任务必须先解决“可见”和“可恢复”

真实求职分析不可能始终在一个 HTTP 请求内完成。它可能包含：

1. 等待用户澄清；
2. 读取或采集市场数据；
3. 加载 DuckDB schema；
4. 生成 SQL；
5. 校验和执行 SQL；
6. SQL 失败后修复并重试；
7. 生成图表；
8. 汇总简历证据并生成报告。

如果没有事件模型，前端只能显示一个静态 spinner；如果没有快照和事件日志，连接断开或进程重启后，系统无法知道任务走到了哪一步。阶段 0 先验证这条长任务骨架。

### 4.3 SSE 与任务执行有明显集成风险

项目设计选择 SSE，是因为前端主要需要服务端到客户端的单向结构化事件流，并且浏览器原生支持 EventSource。可是 SSE 只是传输机制，不会自动解决：

- 后台工作在哪里执行；
- 事件怎样排序；
- 断线怎样恢复；
- 任务完成后怎样查询；
- worker 异常怎样映射为失败事件。

阶段 0 把任务执行和事件传输拆开，先用 fake executor 验证这些基础语义。

### 4.4 避免阻塞事件循环

如果在 async FastAPI handler 中直接调用同步 scraper 或同步 LLM client，一个用户的长任务可能阻塞整个 worker，导致其他请求、心跳和 SSE 连接都无法及时响应。阶段 0 明确“请求线程只负责接入和读取，耗时执行交给后台边界”，为后续接入真实 worker 留出正确方向。

### 4.5 Pydantic 是防御性边界

LLM 输出、外部采集结果和前端请求都不是天然可信的。Pydantic 可以在边界处做：

- 字段存在性校验；
- 类型转换或拒绝；
- 枚举约束；
- 长度和空值约束；
- 额外字段控制；
- 结构化错误返回。

它不能保证业务事实正确，但能让“结构不合法”和“业务内容不正确”被区分处理。

## 五、阶段 0 的整体设计

当前阶段 0 的主要代码分工如下：

| 文件 | 责任 |
| --- | --- |
| backend/app/contracts.py | Pydantic 模型、状态枚举、错误枚举 |
| backend/app/runtime_store.py | JSON 快照、JSONL 事件、顺序和幂等 |
| backend/app/fake_executor.py | 后台 fake 任务执行和事件生成 |
| backend/app/api/routes.py | 创建任务、查询任务、SSE 订阅 |
| backend/tests/test_stage0.py | 契约、持久化、SSE、重连和兼容性测试 |
| data/README.md | 本地数据和运行时文件边界 |
| eval/README.md | 评测目录用途 |
| pyproject.toml | 唯一 Python 依赖真源 |
| .python-version | 固定 Python 3.11 |

整体流程如下：

~~~text
POST /api/tasks
       |
       v
Pydantic 校验 UserRequest
       |
       v
FakeTaskExecutor.create()
       |
       +--> 写入 created 快照和 task.created 事件
       |
       +--> asyncio.create_task(_run(task_id))
                         |
                         v
              running -> step events -> heartbeat
                         |
                         v
                  completed / failed
                         |
                         v
              JSON 快照 + JSONL 事件日志

GET /api/tasks/{task_id}/events
       |
       +--> 读取 Last-Event-ID
       +--> 读取 after_sequence 之后的事件
       +--> SSE id/event/data
       +--> 终态后关闭连接
~~~

这里有两个互补的持久化对象：

### 5.1 快照是“现在是什么状态”

任务快照适合回答：

- 任务目前是什么状态？
- 当前最后一个 sequence 是多少？
- 任务是否已有最终 result？
- 最近一次错误是什么？

快照不适合保留所有历史细节。

### 5.2 事件日志是“发生过什么”

事件日志适合回答：

- 任务经历了哪些阶段？
- 客户端断线前看到哪个事件？
- 某一步什么时候开始和结束？
- 是否发生了 heartbeat、重试或失败？

事件日志采用追加方式，天然适合重放和审计。生产环境中还需要考虑日志分片、保留期限和并发写入，但阶段 0 先验证语义。

## 六、关键代码和函数参数讲解

以下代码以当前实现的核心逻辑为准，代码片段为了学习方便做了适度截取。

### 6.1 TaskStatus：把生命周期变成受约束的类型

~~~python
class TaskStatus(str, Enum):
    CREATED = "created"
    RUNNING = "running"
    WAITING_CLARIFICATION = "waiting_clarification"
    COMPLETED = "completed"
    FAILED = "failed"
    CANCELLED = "cancelled"
~~~

这里继承 str 和 Enum 有两个实际好处：

- JSON 序列化时能够表现为稳定字符串；
- 代码中使用 TaskStatus.RUNNING，而不是到处手写字符串。

WAITING_CLARIFICATION 很重要。它说明“任务没有继续执行”不一定是系统失败，也可能是业务上需要用户提供更多条件。把它和 FAILED 分开，前端才能展示正确的下一步操作。

### 6.2 TargetJobRequest：把搜索条件独立出来

~~~python
class TargetJobRequest(BaseModel):
    keyword: str
    city: str | None = None
    company: str | None = None
    experience: str | None = None
    degree: str | None = None
~~~

参数含义：

- keyword：岗位关键词，例如 AI Agent；
- city：目标城市；
- company：可选公司过滤；
- experience：经验要求；
- degree：学历要求。

把岗位条件独立成模型，而不是把这些字段全部塞到 UserRequest 中，可以让采集、查询和前端表单复用同一个结构。

### 6.3 UserRequest：请求边界和额外字段策略

~~~python
class UserRequest(BaseModel):
    model_config = ConfigDict(extra="forbid")

    task_id: str = ""
    session_id: str
    text: str
    resume_id: str | None = None
    target: TargetJobRequest | None = None

    @field_validator("text")
    @classmethod
    def validate_text(cls, value: str) -> str:
        normalized = value.strip()
        if not normalized:
            raise ValueError("text must not be blank")
        return normalized
~~~

参数和设计点：

- task_id：允许客户端携带已有任务标识，但新建任务时由服务端生成 UUID；
- session_id：关联一次用户会话；
- text：原始自然语言请求，先去除两端空白，禁止空字符串；
- resume_id：只传引用，不把完整简历内容放进任务请求；
- target：结构化岗位条件，可选。

extra="forbid" 的作用是拒绝未声明字段。对于核心状态，这比静默忽略未知字段更安全，因为拼写错误会立即暴露。例如把 session_id 错写成 sesion_id，系统应该报错，而不是创建一个缺少会话标识的任务。

验证器不是为了替代业务验证。它先完成结构层验证，真正的岗位是否存在、关键词是否合理等属于后续业务层。

### 6.4 TaskSnapshot：快照是任务查询接口的稳定输出

~~~python
class TaskSnapshot(BaseModel):
    task_id: str
    status: TaskStatus
    sequence: int = 0
    created_at: datetime
    updated_at: datetime
    result: TaskResult | None = None
    error: FailureInfo | None = None
~~~

关键参数：

- task_id：任务唯一标识；
- status：当前生命周期状态；
- sequence：已经写入的最后一个事件序号；
- created_at：创建时间；
- updated_at：最后状态更新时间；
- result：完成后的结构化结果；
- error：失败时的分类错误。

sequence 放在快照中很有价值：查询任务时，客户端可以知道自己已经看到哪个版本；SSE 重连时也可以把它作为恢复位置的参考。

### 6.5 SseEvent：事件必须同时具备身份和顺序

~~~python
class SseEvent(BaseModel):
    event_id: str
    task_id: str
    sequence: int
    type: str = Field(alias="event_type")
    timestamp: datetime
    payload: dict[str, object] = Field(default_factory=dict)

    model_config = ConfigDict(populate_by_name=True)

    @property
    def event_type(self) -> str:
        return self.type
~~~

字段讲解：

- event_id：事件的全局稳定身份，适合去重和 Last-Event-ID；
- task_id：防止事件被错误地归到另一个任务；
- sequence：同一任务内的严格递增序号，适合重放；
- type：例如 task.created、task.started、step.started、heartbeat、task.completed；
- timestamp：事件发生时间；
- payload：事件的业务内容。

event_id 和 sequence 不能互相替代。event_id 回答“这是不是同一个事件”，sequence 回答“它在这个任务的事件流中位于哪里”。断线恢复主要依赖顺序，而重复事件去重主要依赖身份。

这里的 payload 在阶段 0 中保留为受控的对象映射，以便 fake flow 快速验证协议。进入真实业务后，关键事件应进一步细化为不同的 Pydantic payload 模型，避免所有业务都退化成无约束字典。

### 6.6 RuntimeStore.__init__：延迟创建运行时目录

~~~python
class RuntimeStore:
    def __init__(self, root: Path) -> None:
        self.root = root
        self.tasks_dir = root / "tasks"
        self.events_dir = root / "events"
~~~

root 是运行时存储根目录。当前 fake executor 通过 backend/data/local/runtime 传入它。目录创建采用延迟策略，在第一次读写时确保目录存在，而不是 import 模块时就修改文件系统。

这有几个好处：

- 导入模块不会产生副作用；
- 测试可以传入临时目录；
- 生产环境可以替换根路径；
- 运行时数据集中在 data/local/runtime，便于 Git 忽略。

### 6.7 save_snapshot：临时文件加原子替换

快照保存的核心思想如下：

~~~python
def save_snapshot(self, snapshot: TaskSnapshot) -> None:
    target = self.task_path(snapshot.task_id)
    temporary = target.with_suffix(".json.tmp")
    temporary.write_text(snapshot.model_dump_json(indent=2), encoding="utf-8")
    with temporary.open("rb") as file:
        os.fsync(file.fileno())
    os.replace(temporary, target)
~~~

实际实现还会确保父目录存在，并对序列化和文件操作错误显式抛出异常。

函数参数 snapshot 是已经经过 Pydantic 校验的 TaskSnapshot。写入流程的重要性在于：

1. 先完整写入临时文件；
2. flush 和 fsync，尽量让数据落盘；
3. 使用 os.replace 一次性替换正式文件。

如果直接覆盖正式 JSON，进程可能在写到一半时崩溃，下一次读取会得到半个 JSON。原子替换让读者通常只能看到旧的完整文件或新的完整文件。

这仍然不是分布式事务。它解决的是单机文件的部分写入问题，不解决多进程同时更新同一任务的竞争。

### 6.8 append_event：追加、校验、幂等

Runtime Store 的事件写入需要检查三个问题：

- sequence 是否连续；
- event_id 是否重复；
- 重复 event_id 的内容是否一致。

典型逻辑是：

~~~python
def append_event(self, event: SseEvent) -> None:
    existing = self.find_event(event.task_id, event.event_id)
    if existing is not None:
        if existing == event:
            return
        raise ValueError("event_id already exists with different content")

    last = self.last_sequence(event.task_id)
    if event.sequence != last + 1:
        raise ValueError("event sequence must be contiguous")

    with self.events_path(event.task_id).open("a", encoding="utf-8") as file:
        file.write(event.model_dump_json() + "\n")
        file.flush()
        os.fsync(file.fileno())
~~~

函数参数 event 是单个经过校验的 SseEvent。

为什么重复事件可以幂等返回？在网络重试、worker 重启或调用方重复提交时，同一事件可能再次到达。如果内容完全相同，返回成功不会破坏日志；如果 event_id 相同但内容不同，则必须报错，因为这表示事件身份被复用或状态发生冲突。

为什么不能允许跳号？如果已经写入 sequence 1，再直接写 sequence 3，sequence 2 可能丢失。阶段 0 宁可显式失败，也不静默制造一个无法可靠恢复的事件流。

### 6.9 list_events：按游标读取事件

~~~python
def list_events(
    self,
    task_id: str,
    after_sequence: int = 0,
) -> list[SseEvent]:
    return [
        event
        for event in self.all_events(task_id)
        if event.sequence > after_sequence
    ]
~~~

after_sequence 的含义是“只返回序号严格大于该值的事件”。如果客户端最后成功收到 sequence 5，重连时请求 after_sequence=5，就只会收到 6、7、8……，不会重复发送已经确认的前五个事件。

当前 SSE endpoint 同时支持 HTTP 的 Last-Event-ID。阶段 0 使用 event_id 查询其对应 sequence，再从下一个 sequence 开始重放。这样可以同时兼容浏览器 EventSource 的标准恢复语义和内部序号模型。

### 6.10 FakeTaskExecutor.__init__：注入存储和步长

~~~python
class FakeTaskExecutor:
    def __init__(
        self,
        store: RuntimeStore,
        step_delay: float = 0.02,
    ) -> None:
        self.store = store
        self.step_delay = step_delay
        self.tasks: dict[str, asyncio.Task[None]] = {}
~~~

参数说明：

- store：依赖注入的 RuntimeStore，便于测试时使用临时目录；
- step_delay：每个 fake 步骤之间的异步延迟，默认很短，避免测试变慢；
- tasks：保存当前进程中已调度的 asyncio Task。

这里的 fake executor 不是最终的任务队列。它只用于验证“API 返回”和“后台执行”之间的边界。生产环境需要考虑进程重启、并发限制、取消、重试、worker 心跳和任务队列持久化。

### 6.11 create：先落库，再调度后台执行

核心顺序是：

~~~python
async def create(self, request: UserRequest) -> TaskSnapshot:
    task_id = str(uuid4())
    now = datetime.now(timezone.utc)
    snapshot = TaskSnapshot(
        task_id=task_id,
        status=TaskStatus.CREATED,
        sequence=0,
        created_at=now,
        updated_at=now,
    )
    self.store.save_snapshot(snapshot)
    self._record(snapshot, "task.created", {"session_id": request.session_id})
    self.tasks[task_id] = asyncio.create_task(self._run(task_id))
    return self.store.load_snapshot(task_id)
~~~

设计要点：

1. 服务端生成 task_id，不能信任客户端任意覆盖；
2. 先创建任务快照和 created 事件；
3. 再调度后台 coroutine；
4. API 立即返回任务快照。

这就是 HTTP 202 Accepted 的合理场景：请求已经被接受并创建任务，但最终结果尚未完成。客户端应该使用返回的 task_id 订阅 SSE 或查询快照，而不是等待 POST 请求阻塞到最终报告完成。

### 6.12 _run：模拟真实长任务的状态转换

fake executor 中的 _run 会模拟以下步骤：

~~~text
created
  -> running
  -> validate_contract
  -> run_fake_work
  -> assemble_result
  -> completed
~~~

每个步骤通常产生：

- step.started；
- 若干 heartbeat；
- step.completed。

最后生成一个最小 TaskResult 并写入 completed 快照。如果执行中发生异常，则将任务更新为 failed，记录 FailureInfo，并发出 task.failed 事件。

这里没有把异常吞掉。异常必须转换为可观察的失败状态，并保留可定位的错误信息；否则前端可能永远等待一个没有终点的任务。

### 6.13 _record：事件和快照的统一更新入口

record 函数承担单次状态变更的公共逻辑。它的典型参数是：

- snapshot：变更前或当前的 TaskSnapshot；
- event_type：事件类型；
- payload：事件业务数据；
- 可选的新状态、结果或错误信息。

它会：

1. 根据当前 sequence 生成下一个 sequence；
2. 生成新的 event_id 和 timestamp；
3. 构造并校验 SseEvent；
4. 追加事件；
5. 更新快照的 sequence 和 updated_at；
6. 将快照持久化。

集中处理可以避免不同步骤重复实现“先写事件还是先写快照”的细节，也减少序号计算错误。

不过需要明确：JSON 快照和 JSONL 事件并不是一个真正的数据库事务。若进程恰好在两个文件写入之间崩溃，生产实现需要增加恢复扫描、事务日志或换用支持事务的存储。阶段 0 的目标是先暴露这一边界，而不是假装它不存在。

### 6.14 POST /api/tasks：API 层只做接入和调度

创建任务的路由大致承担三件事：

~~~python
@router.post("/tasks", status_code=202)
async def create_task(payload: UserRequest) -> TaskSnapshot:
    return await fake_executor.create(payload)
~~~

参数 payload 由 FastAPI 根据 UserRequest 自动完成请求体解析和 Pydantic 校验。路由不直接运行 scraper、不直接调用阻塞型模型客户端，也不在 HTTP 请求中等待 fake flow 的最终结果。

如果请求结构不合法，FastAPI 会在进入 executor 之前返回校验错误；如果任务内部失败，则由任务状态和失败事件表达。这是“请求错误”和“异步任务错误”的边界。

### 6.15 GET /api/tasks/{task_id}/events：SSE endpoint

SSE 路由的核心职责是：

1. 读取 task_id；
2. 检查任务是否存在；
3. 解析 Last-Event-ID；
4. 读取该位置之后的 JSONL 事件；
5. 将事件编码为 SSE 的 id、event 和 data；
6. 没有新事件时异步等待一小段时间；
7. 任务进入终态且已发送完相关事件后关闭连接。

发送格式类似：

~~~text
id: event-uuid
event: step.started
data: {"task_id":"...", "sequence":4, "payload":{...}}

~~~

data 是 JSON 字符串，而不是 Python repr。前端可以稳定地 JSON.parse。

路由的函数参数包括：

- task_id：路径参数，指定任务；
- request：Starlette Request，用于检查客户端是否断开；
- last_event_id：从 HTTP Last-Event-ID header 读取的事件身份。

连接检查和异步 sleep 很重要。不能使用同步 sleep，否则会阻塞事件循环；也不能在客户端已经断开后无限循环。

### 6.16 兼容旧的 GET /api/tasks/{task_id}

项目原先存在 AskData 查询任务相关的路由。阶段 0 增加 fake task 查询时，没有简单删除旧能力，而是保留兼容分支：

- 如果 task_id 命中 Runtime Store，就返回阶段 0 的 TaskSnapshot；
- 如果没有命中 fake task，则继续执行原有的认证和查询逻辑。

这体现了增量迁移原则：阶段 0 先增加新的任务模型，不破坏原有 AskData 接口。后续所有业务统一到 TaskSnapshot 后，再删除兼容分支。

## 七、SSE 协议、心跳和断线恢复

### 7.1 事件类型

当前 fake flow 至少覆盖：

- task.created；
- task.started；
- step.started；
- heartbeat；
- step.completed；
- task.completed；
- task.failed。

真实业务可以继续扩展：

- crawl.queued；
- crawl.progress；
- crawl.risk；
- schema.loaded；
- sql.generated；
- sql.validation_failed；
- sql.retry；
- report.chunk；
- clarification.required。

事件类型应该描述可展示的系统动作，不应输出模型隐藏思维链。用户需要的是“正在加载岗位数据”“SQL 校验失败，正在修复”，而不是未经筛选的内部推理文本。

### 7.2 为什么需要 heartbeat

长任务可能一段时间没有业务事件，例如等待浏览器登录、等待 worker 或执行一条慢查询。heartbeat 可以：

- 保持 HTTP 连接活跃；
- 让前端知道任务仍在运行；
- 让代理和负载均衡器不把连接判定为闲置；
- 帮助监控判断 worker 是否还在工作。

heartbeat 不代表业务进度增加。它只表示“连接和任务仍然有活动”，不能用来替代真实的步骤事件。

### 7.3 Last-Event-ID 恢复过程

假设客户端已经收到：

~~~text
sequence 1, 2, 3, 4, 5
~~~

客户端在 sequence 5 之后断线。浏览器重连时携带：

~~~text
Last-Event-ID: event-id-for-sequence-5
~~~

服务端执行：

1. 根据 event_id 找到 sequence 5；
2. 调用 list_events(task_id, after_sequence=5)；
3. 重新发送 sequence 6 及之后的事件；
4. 不重复发送 1 到 5；
5. 如果任务已经完成，补发完成事件后关闭流。

如果 Last-Event-ID 不存在或不属于该任务，服务端应返回明确错误或从安全的默认位置开始，而不能把另一个任务的事件混入当前流。

### 7.4 SSE 与轮询的关系

SSE 是传输层。任务快照和事件模型才是业务层。SSE 不可用时，前端可以通过 GET /api/tasks/{task_id} 轮询同一个快照，或者通过事件查询接口拉取同一事件模型。

不能为轮询重新设计一套独立任务状态，否则两种传输模式会逐渐产生不同语义，最终难以维护。

## 十、实现中的设计边界和后续改进

### 10.1 当前 fake executor 是单进程模型

asyncio.create_task 适合 Spike 和本地开发，但进程退出后任务不会自动从中断处继续。Runtime Store 让已写入的快照和事件可读，不等于它已经具备生产级 worker 恢复能力。

后续可以把 executor 替换为：

- 受控进程 worker；
- Redis、数据库或消息队列；
- LangGraph 的持久化运行时；
- 具有租约、重试、取消和幂等键的任务调度系统。

替换时应保持 UserRequest、TaskSnapshot 和 SseEvent 的外部语义稳定。

### 10.2 两阶段写入不是完整事务

事件和快照分别写入 JSONL 与 JSON，中间存在进程崩溃窗口。后续可以：

- 使用单独的状态数据库；
- 使用事务表和事件表；
- 在启动时扫描事件重建快照；
- 为事件和快照增加版本号；
- 引入 outbox 或事件溯源机制。

阶段 0 的价值在于把问题显式化，并通过接口隔离存储实现。

### 10.3 事件 payload 需要继续类型化

当前事件外层结构严格，payload 为了快速 Spike 保留了通用映射。接入真实业务后，应定义：

- CrawlProgressPayload；
- SqlAttemptPayload；
- ReportChunkPayload；
- ClarificationPayload；
- FailurePayload。

这样前端和后端能够分别对每种事件做严格校验，减少字符串字段和隐式约定。

### 10.4 生产环境需要鉴权和隔离

阶段 0 的 fake route 为了测试可用性放宽了部分原有访问路径，但生产环境必须：

- 校验 session_id 与当前用户；
- 防止用户读取其他人的 task_id；
- 对 SSE 做权限检查；
- 限制任务创建频率；
- 不在事件和日志中输出完整简历；
- 对 resume_id 和本地文件做生命周期管理。

尤其是简历属于高敏感个人数据。resume_id 应该是引用，SSE payload 和日志不应携带完整简历文本；发送给外部 LLM 前应进行 PII 脱敏。

## 十一、模拟求职面试问答

下面的问题按照“面试官追问”的方式组织。回答重点不是背代码，而是说明工程取舍、边界和验证证据。

### Q1：为什么要把阶段 0 放在最前面？

答：因为项目的主要风险不是单个 Agent 能否调用模型，而是多个长任务组件能否共享稳定契约、异步执行边界和可恢复事件。阶段 0 先用 Pydantic、任务状态、SSE、Runtime Store 和 fake executor 验证最小闭环，避免真实采集、NL2SQL 和报告 Agent 各自发明状态和错误格式，后期再花大量时间返工。

### Q2：为什么阶段 0 不直接接入真实 BOSS 采集？

答：BOSS 采集依赖浏览器、登录态、Cookie 和风控，外部不确定性很高。如果把它作为阶段 0 的前置条件，契约和流式协议的验证会被环境问题阻塞。fake executor 可以稳定地产生 created、running、step、heartbeat、completed 和 failed 事件，先证明任务系统正确；真实采集作为 worker 在同一协议上并行接入。

### Q3：Spike 和最终实现有什么区别？

答：Spike 的目标是验证高风险设计能否工作，不是提供最终吞吐和可靠性。当前用本地 JSON/JSONL 和 asyncio.create_task 验证接口与语义；生产实现可能使用数据库、消息队列、专用 worker、事务和水平扩展。但生产实现应尽量保持阶段 0 确定的外部契约，替换内部执行器和存储。

### Q4：为什么使用 Pydantic，而不是直接传 dict？

答：dict 没有字段约束、枚举约束和统一错误语义，拼写错误会静默传播。Pydantic 可以在 API、Agent 边界和持久化读取时验证结构，并把外部不可信数据转换成明确的模型。它不能保证业务事实正确，但可以把结构不合法和内容不正确区分开。

### Q5：为什么选择 SSE，而不是 WebSocket？

答：本项目的主要需求是服务端到浏览器的单向事件流，SSE 由浏览器原生支持，协议简单，自动重连语义明确，也方便代理和 HTTP 基础设施处理。WebSocket 更适合双向低延迟交互，但会增加连接管理和协议复杂度。用户澄清仍然可以通过普通 REST 请求完成，不必为了进度流引入双向通道。

### Q6：SSE 断线后如何恢复？只依赖浏览器自动重连够吗？

答：不够。浏览器可以发送 Last-Event-ID，但服务端必须保存稳定 event_id、同一任务内递增 sequence 和可重放事件日志。服务端根据 Last-Event-ID 找到对应 sequence，从下一个事件开始发送。阶段 0 用 JSONL 实现这个语义，并在测试中验证重连不会从头重复或跳过事件。

### Q7：event_id 和 sequence 为什么都需要？

答：event_id 是事件身份，用于判断事件是否重复；sequence 是任务内位置，用于排序、游标和断点恢复。event_id 解决“是不是同一个”，sequence 解决“在第几个”。仅有 UUID 无法高效表达顺序，仅有整数序号也不适合跨系统去重。

### Q8：heartbeat 是业务进度吗？

答：不是。heartbeat 只表示连接和执行器仍有活动，主要用于保持连接、避免代理超时和监控存活。业务进度必须由 step.started、step.completed、crawl.progress 等事件表达，不能用 heartbeat 冒充实际进度。

### Q9：为什么快照用 JSON，事件用 JSONL？

答：快照适合按任务读取当前状态，一个任务一个 JSON 文件即可。事件适合追加和顺序重放，JSONL 每行一个事件，便于流式追加和逐条读取。两者职责不同：快照回答“现在是什么”，事件日志回答“发生过什么”。

### Q10：为什么写 JSON 快照需要临时文件和 os.replace？

答：直接覆盖可能在进程崩溃时留下半个 JSON，下一次读取会失败。先写临时文件、flush、fsync，再原子替换，读者通常只能看到旧的完整文件或新的完整文件。它不能解决多进程事务问题，但能解决单机部分写入问题。

### Q11：如何保证事件顺序？

答：每个任务维护 sequence，首次事件从 1 开始，后续必须等于上一条加 1。append_event 写入前校验连续性，list_events 按 sequence 过滤和排序。发现跳号时显式报错，而不是把数据写成一个看似成功但无法恢复的事件流。

### Q12：重复事件怎么办？

答：先按 task_id 和 event_id 查找。如果已有事件内容完全相同，则幂等返回；如果 event_id 相同但内容不同，则报错。这能容忍网络重试，同时避免事件身份被错误复用。

### Q13：如何证明 SSE endpoint 没有阻塞 FastAPI？

答：代码层面，SSE 路由只读取事件和异步等待，使用 asyncio.sleep，不调用同步 scraper 或同步 invoke；后台任务通过 asyncio.create_task 调度。测试层面，可以在任务运行期间读取多个事件和 heartbeat，说明事件循环仍能处理持续连接。生产环境还要把真实阻塞工作移到 worker、线程池或进程边界，并做并发压测。

### Q14：asyncio.create_task 能作为生产任务队列吗？

答：不能。它适合阶段 0 的本地 Spike，因为实现简单且可以验证 API 与后台执行的解耦。但它受单进程生命周期影响，进程重启时任务会丢失，也缺少持久化调度、跨实例去重和可靠重试。生产环境需要持久化队列或 worker runtime。

### Q15：如果写入事件后、写入快照前进程崩溃怎么办？

答：当前 JSON 和 JSONL 分开写，确实存在一致性窗口。阶段 0 不把它伪装成完整事务，而是明确记录该边界。后续可以使用事务数据库、事件表、启动重放重建快照、outbox 或版本校验。关键是 RuntimeStore 通过接口隔离了存储实现，业务层不需要重写。

### Q16：为什么要保留旧的 GET /api/tasks/{task_id} 逻辑？

答：项目原来有 AskData 查询相关接口。阶段 0 是增量基础设施，不应该为了接入 fake task 而无意破坏旧功能。因此路由先判断 task_id 是否是新 Runtime Store 任务；不是时继续执行旧的认证和查询分支。等业务统一到新任务模型后再删除兼容代码。

### Q17：为什么 POST 创建任务返回 202，而不是 200？

答：202 Accepted 表示请求已被接受，但异步工作尚未完成。返回 200 容易让调用者误以为最终报告已经生成。202 配合 task_id、SSE 和最终快照，准确表达了长任务的生命周期。

### Q18：如何处理简历隐私？

答：任务请求只传 resume_id，不把完整简历放进事件和日志；原始简历默认本地短期保存；发送给外部 LLM 前脱敏姓名、电话、邮箱和地址；事件只展示结构化执行轨迹，不输出完整简历文本；生产 API 还必须校验用户是否有权访问 resume_id 和 task_id。

### Q19：单进程实现如何扩展到多个 worker？

答：需要把任务状态、事件追加和执行调度从进程内存迁移到共享可靠组件，例如数据库、Redis 或消息队列，并为事件写入增加并发控制、幂等键和版本检查。SSE 连接所在的进程不能只看自己的内存，而要订阅共享事件源。阶段 0 的 contract 和 endpoint 语义可以保留。

### Q20：如果部署环境不支持 SSE 怎么办？

答：使用同一 TaskSnapshot 和 SseEvent 任务模型做 REST 轮询或事件拉取。SSE 是传输层，不应重新设计一套状态。轮询只是降低实时性，不能改变 created、running、completed、failed 等语义。

### Q21：阶段 0 的完成证据是什么？

答：不是“安装了 sse-starlette”，而是有可运行闭环和测试证据：uv sync 成功，uv lock --check 成功，162 个测试通过；手工请求能创建任务并返回 202，SSE 返回有序事件，包含 heartbeat 和 task.completed，Last-Event-ID 能恢复，最终 GET 能读到 completed 快照和 result。

### Q22：下一步如何把 fake executor 换成真实 Agent 流程？

答：先保持 UserRequest、TaskSnapshot、SseEvent 和错误语义不变，把 _run 内部替换成受控 worker 或 LangGraph runtime。每个 Agent 节点只接受明确的 Pydantic 输入并返回明确的输出；Coordinator 将节点状态映射为事件；真实采集、SQL 自修正和报告生成继续通过同一个事件记录入口对外发布。完成后增加超时、取消、重试、worker 恢复和权限测试。

### Q23：为什么事件 payload 目前还不是所有地方都用独立 Pydantic 模型？

答：阶段 0 的第一目标是验证统一事件外壳、顺序、持久化和重连。payload 先使用受控映射能降低 Spike 成本，但这不是最终的类型边界。真实业务接入后，应为 crawl、SQL、报告和澄清事件定义独立 payload 模型，并在事件类型和 payload 类型之间建立映射。

### Q24：如果 LLM 返回了错误格式，阶段 0 的契约能解决吗？

答：契约可以拒绝结构不合法的结果，但不能自动修复所有模型错误。真实 LLM gateway 应对响应做 Pydantic 校验，失败时记录结构化错误，按策略重试或转为任务失败；不能直接把未经验证的模型文本写入核心状态。阶段 0 的防御性契约为这套处理提供统一落点。

## 十二、面试中的简短表达

### 30 秒版本

阶段 0 是我为长任务 Multi-Agent 系统搭的工程地基。我先用 Pydantic 固定输入、任务状态、失败信息和 SSE 事件契约，再用一个异步 fake executor 验证任务创建、后台执行、heartbeat、事件顺序和 Last-Event-ID 断线恢复。任务快照用原子写 JSON，事件用 append-only JSONL 保存。这样真实 BOSS 采集、NL2SQL 和职业报告 Agent 后续只需要接入同一个任务和事件模型，不需要各自发明协议。

### 2 分钟版本

这个项目的真实工作流包含采集、ETL、NL2SQL、SQL 自修正和报告生成，单个 HTTP 请求无法可靠承载整个过程。阶段 0 先处理跨模块风险：用 Pydantic 模型作为边界，用枚举固定任务和采集状态，用 SSE 事件表示可展示的结构化轨迹，用 JSON 快照保存当前状态，用 JSONL 事件日志支持重放。API 创建任务后返回 202 和 task_id，异步 executor 在后台产生 created、running、step、heartbeat、completed 或 failed 事件。SSE 读取 Last-Event-ID，并从下一个 sequence 重放，因此断线不会丢进度。实现上用 fake flow 隔离真实浏览器和 LLM 的不确定性，测试覆盖契约校验、事件连续性、幂等、SSE 和重连。当前实现是单进程 Spike，不把 asyncio.create_task 或本地文件误称为生产任务队列；后续可以替换为持久化 worker、数据库或消息队列，同时保持外部契约稳定。
