## 1. 阶段四的任务、作用与存在原因

### 1.1 设计文档中的阶段四任务

设计文档把阶段四定义为“评测、前端与演示”，原计划为 3–4 天加缓冲时间。当前实现已经覆盖以下内容：

| 任务 | 当前实现 | 解决的问题 |
|---|---|---|
| `seed / eval_dev / eval_test` 三路数据分离 | `eval/data/*.jsonl` 与 `eval/dataset.py` | 防止把开发样例、演示样例和最终报告混在一起 |
| 至少 50 个 NL2SQL case | 6 个 seed、20 个 dev、30 个 test，共 56 个 case | 让准确率、延迟和修复率有基本统计意义 |
| pytest 风格评测 Runner | `eval/runner.py`、`backend/tests/test_stage4.py` | 自动计算首轮准确率、最终准确率、恢复率、尝试次数、P50/P95、token/cost |
| 消融实验 | `run_ablation()` 与 `--ablation` | 分析纠错和 few-shot 分别带来了什么收益 |
| 前端职责拆分 | `ClarificationPanel.vue`、`ExecutionTimeline.vue`、`DemoTaskPanel.vue` | 降低 `App.vue` 的新增复杂度，并分别展示澄清、SQL 尝试和任务事件 |
| 接入 SSE 执行轨迹 | `api.streamTaskEvents()` 与 `DemoTaskPanel.vue` | 让长任务不再只能显示“等待中”，而能显示事件序列 |
| Clarification 交互 | `ClarificationPanel.vue` | 把 Agent 的澄清问题变成可点击的产品交互 |
| ECharts 与 Markdown 渲染接入 | 保留并接入现有 `AnalysisChart`、`MarkdownReport` | 让结果不仅有表格，也有图表和可读报告 |
| CLI/任务 API 状态展示 | `DemoTaskPanel.vue` 调用 `/api/tasks` 与 SSE | 展示后台任务的创建、执行、完成和失败状态 |
| 一键启动与离线演示 | `make setup`、`docs/demo_stage4.md` | 面试现场不依赖实时爬取、第三方登录或网络模型调用 |
| README、免责声明、数据和隐私说明 | README 与阶段四演示文档 | 让别人知道项目如何运行、数据从哪里来、哪些指标不能过度解读 |

阶段四不是简单地“做一个页面”。它实际上补齐了工程项目中经常被忽略的三层能力：

1. **测量能力**：知道系统现在到底有多好，而不是凭主观感觉说“效果不错”。
2. **可观测能力**：知道一次请求经过了哪些步骤、失败在哪里、是否发生了 SQL 修复。
3. **可交付能力**：别人可以按 README 启动、复现评测，并在没有线上依赖的情况下看到完整流程。

### 1.2 为什么前面阶段完成后，还必须有阶段四

阶段一到阶段三已经建立了主要能力：

- 阶段一建立了数据、ETL、DuckDB、Schema Catalog 和基础 NL2SQL 能力。
- 阶段二引入了全量 Schema、SQL 计划、自修正、权限和任务编排等更接近工程系统的能力。
- 阶段三把 Agent 组织成 CareerAgent 的最小闭环，开始具备“输入问题—调用工具—形成结果”的产品雏形。

但是，仅仅能够运行并不代表项目已经完成。没有阶段四时，项目会有下面这些明显问题：

#### 问题一：没有可重复的效果结论

如果每次都手工输入几个问题，只展示几个成功截图，就无法回答以下面试问题：

- 首轮 SQL 的准确率是多少？
- 纠错之后提升了多少？
- 哪些错误可以恢复，哪些错误无法恢复？
- 平均会尝试几次？P95 延迟是否明显变差？
- 额外的 token 和成本是多少？

阶段四用固定数据集、固定 fixture 和固定配置回答这些问题。

#### 问题二：无法区分“初始能力”和“纠错能力”

最终结果正确，可能有两种完全不同的原因：

- 模型第一遍就生成了正确 SQL；
- 第一遍出错，但系统根据数据库错误或验证结果修复成功。

只有记录 `first_pass_correct`、`final_correct` 和 `recovered`，才能知道自修正模块是否真的有效，而不是只看最终成功率。

#### 问题三：系统内部过程不可见

Agent 不是一个黑盒函数。用户通常需要知道：

- 系统是否理解了问题；
- 是否需要澄清；
- 生成了几次 SQL；
- 哪一次发生了 schema、验证或数据库错误；
- 最终返回的结果是从哪一步得到的。

前端阶段把这些内部过程转成时间线、澄清面板和任务事件。

#### 问题四：演示过度依赖外部环境

实时爬虫、外部 LLM API、登录态和网络服务都会给面试演示带来风险。如果演示机器没有 API Key、网络不稳定、登录过期，项目就无法展示真正的价值。

所以本阶段把演示路径设计成离线可复现路径：

```text
固定 fixture
   ↓
本地 ETL
   ↓
本地 DuckDB
   ↓
确定性评测 SQL 生成器
   ↓
准确率 / 修复率 / 延迟 / 成本报告
```

这里的确定性生成器不是为了假装成真实大模型，而是为了隔离评测框架本身的正确性。将来替换成真实模型客户端时，数据集、指标和报告接口可以保留。

### 1.3 阶段四的核心目标

可以把阶段四总结成一句话：

> 把“Agent 能够跑起来”升级为“Agent 的效果可以被测量、过程可以被解释、项目可以被别人复现”。

对应到软件工程中的目标，就是：

| 目标 | 具体做法 |
|---|---|
| 可重复 | 固定 JSONL 数据集、固定 seed、离线 fixture、临时数据库 |
| 可比较 | 四组消融配置、统一指标模型、统一输出 JSON |
| 可诊断 | 每个 case 记录首轮结果、最终结果、尝试次数和错误类型 |
| 可扩展 | 评测 Runner 接受模型名、成本参数和开关 |
| 可演示 | Makefile、SSE 事件流、前端状态组件、演示文档 |
| 可审计 | Pydantic `extra="forbid"`、重复 ID 检查、权限 scope、测试 |

### 1.4 本阶段的边界

阶段四有明确的 MVP 边界，不能把尚未实现的内容说成已经实现：

- 评测默认不调用真实在线大模型；`eval/runner.py` 使用确定性 SQL 生成器注入 `QueryAgent`。
- 评测 fixture 是脱敏/合成数据，不代表真实招聘网站的全量分布。
- 当前前端把 QueryResult 中的 SQL 尝试时间线和任务 API 的 SSE 任务流都展示出来，但二者是两条不同的接口路径；它们已经可以共同完成演示，但不是把每一次同步查询自动改造成了后台异步任务。
- 管理页属于可选项，本阶段没有为了演示强行实现完整管理后台。
- 复杂的真实模型成本计费、跨多个真实数据集的统计置信区间和端到端浏览器测试仍属于后续增强项。

这种边界意识很重要。面试中应明确说“当前实现到哪里”，再说“如果继续生产化，下一步会怎么做”，而不是夸大功能。

## 2. 从阶段一到阶段四：项目如何完成闭环

阶段四最好放在整个项目生命周期中理解，而不是孤立理解。

```text
阶段一：数据与最小 NL2SQL
    ├─ ETL
    ├─ DuckDB
    ├─ Schema Catalog
    └─ 基础 QueryAgent
              ↓
阶段二：可靠性与编排
    ├─ 全量 Schema
    ├─ QueryPlan
    ├─ Guard / Validate / Execute
    ├─ SQL 自修正
    ├─ AccessScope
    └─ 任务状态模型
              ↓
阶段三：CareerAgent 最小闭环
    ├─ 多步骤 Agent
    ├─ 工具调用
    ├─ 报告和结果展示
    └─ 前后端基本连接
              ↓
阶段四：评测、观测与交付
    ├─ 50+ case 离线基准
    ├─ 首轮 / 最终 / 恢复率
    ├─ 消融实验
    ├─ Clarification / Timeline / SSE
    ├─ 一键启动
    └─ README、演示和面试材料
```

其中阶段四并没有替代前面的核心逻辑，而是给前面的逻辑增加了“证据层”和“产品层”。

### 2.1 评测闭环

```text
eval/data/*.jsonl
    ↓ load_dataset()
Pydantic EvalCase
    ↓ run_benchmark()
临时目录 + 本地 ETL
    ↓
DuckDB + SchemaCatalog
    ↓
QueryAgent（首轮 / 纠错后）
    ↓
执行结果规范化
    ↓
CaseMetrics
    ↓
BenchmarkResult
    ↓
JSON 文件 / 终端 / pytest 断言
```

### 2.2 产品闭环

```text
用户输入自然语言
    ↓
App.vue / 查询面板
    ├─ 需要澄清 → ClarificationPanel → 选择选项
    ├─ 返回查询结果 → ResultTableCard / AnalysisChart / MarkdownReport
    └─ 后台演示任务 → DemoTaskPanel
                              ↓
                    POST /api/tasks
                              ↓
                    GET /api/tasks/{id}/events
                              ↓ SSE
                    task.created / step / completed
                              ↓
                    GET /api/tasks/{id}
```

查询结果中的 `ExecutionTimeline` 解释 QueryAgent 的 SQL 尝试；`DemoTaskPanel` 解释通用任务 API 的事件流。这样设计可以复用前面阶段已有的同步查询接口，同时把阶段四要求的 SSE 状态展示独立验证出来。

### 3.3 分层原则

这是一种低风险的渐进式拆分：保留原有查询、图表、Markdown 和结果表格逻辑，优先把阶段四新增的职责隔离出去，避免在一个阶段内重写整个前端。

## 4. 评测数据集设计

### 4.1 为什么使用三路数据集

三路数据集分别承担不同职责：

| 数据集 | 当前规模 | 目的 | 是否用于最终结论 |
|---|---:|---|---|
| `seed` | 6 | 快速冒烟测试、演示和开发环境验证 | 否，主要用于快速反馈 |
| `eval_dev` | 20 | 调试数据集构造、修复规则和指标逻辑 | 否，允许开发阶段反复查看 |
| `eval_test` | 30 | 稳定的阶段四测试集 | 是，但仍然属于离线合成 fixture |

加起来是 56 个 case，满足设计文档要求的至少 50 个 case。`dev` 和 `test` 的原始模板数量较少，但通过 `repeat` 展开成多个稳定 ID，从而避免手工复制大量几乎相同的 JSON。

真实项目中应该尽量保证 test 数据不参与提示词设计和规则调试；本项目是学习型项目，当前数据规模有限，因此在笔记和 README 中明确记录其“离线合成 benchmark”的定位。

### 4.2 `EvalCase` 的严格模型

源码中的核心输入模型如下：

```python
class EvalCase(BaseModel):
    model_config = ConfigDict(extra="forbid")

    case_id: str = Field(min_length=1, max_length=100)
    query: str = Field(min_length=1, max_length=5000)
    expected_sql: str = Field(min_length=1, max_length=20000)
    first_sql: str = Field(min_length=1, max_length=20000)
    repair_sql: str = Field(min_length=1, max_length=20000)
    few_shot_sql: str | None = Field(default=None, max_length=20000)
    error_kind: str | None = Field(default=None, max_length=50)
    repeat: int = Field(default=1, ge=1, le=20)
```

每个字段的含义如下：

| 字段 | 含义 |
|---|---|
| `case_id` | case 的稳定标识；展开重复样本时会生成 `case_id-01` 这样的 ID |
| `query` | 用户输入的自然语言问题 |
| `expected_sql` | oracle SQL，用于在同一个 fixture 上生成期望结果 |
| `first_sql` | 关闭纠错或执行首轮时的 SQL |
| `repair_sql` | 首轮失败后，模拟修复阶段生成的 SQL |
| `few_shot_sql` | 开启 few-shot 时使用的候选 SQL，可为空 |
| `error_kind` | 预期错误类型，例如 schema/验证/数据库错误的分类标签 |
| `repeat` | 该模板展开多少次；限制在 1 到 20 之间 |

这里把 SQL 作为数据集中的显式字段，是为了让评测框架能够在不调用在线 LLM 的情况下，独立验证“指标计算、错误恢复和消融开关”是否正确。它不是在声称真实模型已经提前知道答案。

### 4.3 为什么 `extra="forbid"`

评测数据属于实验输入。若 JSONL 中多写了一个拼写错误字段，例如把 `expected_sql` 写成 `expect_sql`，宽松解析可能悄悄忽略该字段，直到评测结果异常时才发现。

`extra="forbid"` 让数据契约更严格：

```text
未知字段 → 立刻校验失败 → 指向具体数据行
```

这体现了项目整体的防御式编程原则：外部数据、LLM 输出和配置都不能默认可信。

### 4.4 数据加载与重复展开

`eval/dataset.py` 的逻辑可以概括为：

```python
def load_dataset(name: DatasetName, root: Path = DATA_ROOT) -> EvalDataset:
    validate_dataset_name(name)
    path = root / f"{name}.jsonl"

    cases: list[EvalCase] = []
    seen_ids: set[str] = set()
    for line_number, line in enumerate(path.read_text().splitlines(), start=1):
        case = EvalCase.model_validate(json.loads(line))
        for index in range(1, case.repeat + 1):
            expanded_id = case.case_id if case.repeat == 1 else f"{case.case_id}-{index:02d}"
            if expanded_id in seen_ids:
                raise ValueError(f"duplicate case id: {expanded_id}")
            seen_ids.add(expanded_id)
            cases.append(case.model_copy(update={"case_id": expanded_id, "repeat": 1}))

    if name in {"eval_dev", "eval_test"} and len(cases) < 10:
        raise ValueError(f"{name} must contain at least 10 cases")
    return EvalDataset(name=name, cases=cases)
```

实际源码还会处理文件不存在、JSON 解析失败和跨数据集重复 ID。`load_all_datasets()` 会加载三路数据，并要求 `eval_dev + eval_test >= 50`。

这种实现有三个好处：

1. 文件层面仍然是可读、可审查的 JSONL。
2. 运行时得到的是经过 Pydantic 验证的对象，而不是核心流程中的裸 `dict`。
3. `repeat` 展开后的 ID 是稳定的，可以定位单个失败 case。

### 4.5 case 覆盖的能力和错误类型

当前 case 覆盖了以下典型问题：

- 统计招聘岗位数量。
- 按城市、学历和经验分组。
- 过滤上海等具体城市。
- 处理薪资区间、薪资周期和平均薪资。
- 查询岗位详情、技能分组和月份薪资。
- 查询最高薪资、可谈薪资和详情表。
- 通过故意使用 `missing_field` 等错误字段，触发纠错路径。
- 通过首轮语义不正确但语法可执行的 SQL，验证 few-shot 开关的影响。

这说明评测不仅覆盖“SQL 能否执行”，还尝试覆盖“结果是否等价”和“纠错/示例是否有帮助”。不过当前 oracle 仍来自固定 fixture，后续还应增加更多数据分布、同义问法、空结果、边界日期和权限拒绝案例。

## 5. 评测 Runner 的实现

### 5.1 Runner 的责任边界

`eval/runner.py` 不是另写一个 Agent，而是负责实验控制：

1. 准备隔离的临时数据库。
2. 用统一权限 scope 创建 Schema Catalog 和 QueryAgent。
3. 分别运行首轮和最终流程。
4. 执行 expected SQL，得到 oracle 结果。
5. 对比实际结果和 oracle 结果。
6. 记录尝试次数、延迟、token 估算、cost 估算和错误类型。
7. 输出 `BenchmarkResult`，供命令行、JSON 和 pytest 使用。

它不应该把生产业务逻辑复制一遍。评测 Runner 复用 `run_etl`、`DuckDbEngine`、`QueryAgent`、`SchemaCatalogBuilder` 和 `AccessScope`，这样测到的是实际 Agent 组合，而不是一个完全不同的玩具实现。

### 5.2 每次运行使用临时目录和本地 ETL

核心思路是每次 benchmark 都从相同 fixture 重建数据库：

```python
def _prepare_database(root: Path) -> Path:
    database_root = root / "databases"
    raw_root = root / "raw"
    fixture = DATA_ROOT.parents[1] / "data" / "fixtures" / "jobs_seed.json"

    run_etl(
        jobs_path=fixture,
        db_root=database_root,
        raw_root=raw_root,
    )
    return database_root
```

这里的 `root` 是 `TemporaryDirectory` 创建的临时目录。这样做的原因是：

- 不污染开发者本地已有数据库。
- 每个 benchmark 都从同一份输入开始。
- 不会因为上一次测试留下的数据而导致结果漂移。
- 并行运行不同配置时，配置之间不会共享可变数据库状态。

如果直接复用一个持久数据库，测试顺序、旧表、旧缓存甚至失败 case 写入的数据都可能影响后续结果，最终导致“本地能过、换顺序就失败”的问题。

### 5.3 评测用的权限 Scope

Runner 不因为是评测代码就绕过权限系统：

```python
TABLES = frozenset(
    {
        "jobs_market.jobs",
        "jobs_market.job_details",
        "jobs_market.job_skills",
        "jobs_market.crawl_runs",
    }
)


def _scope() -> AccessScope:
    return AccessScope(
        user_id="eval_runner",
        roles=("local",),
        allowed_databases=frozenset({"jobs_market"}),
        allowed_tables=TABLES,
    )
```

关键点是评测必须尽量使用和生产路径相同的安全边界。否则，评测结果可能是“绕过 guard 后的 SQL 执行结果”，无法证明真正的 Agent 在正常权限约束下可用。

### 5.4 确定性 SQL 生成器与 Agent 注入

为了避免评测框架依赖网络和非确定性模型，Runner 构造 `QueryAgent` 时注入一个确定性生成函数：

```python
def _make_agent(
    database_root: Path,
    case: EvalCase,
    max_attempts: int,
    few_shot_enabled: bool,
) -> QueryAgent:
    engine = DuckDbEngine(database_root=database_root, access_scope=_scope())
    catalog_builder = SchemaCatalogBuilder(engine=engine, access_scope=_scope())

    def sql_generator(query: str, previous_error: str | None = None) -> str:
        return _sql_for_case(
            case=case,
            previous=previous_error,
            few_shot=few_shot_enabled,
        )

    return QueryAgent(
        model_client=object(),
        engine=engine,
        catalog_builder=catalog_builder,
        max_attempts=max_attempts,
        sql_generator=sql_generator,
    )
```

这里 `model_client=object()` 的含义不是让 `object()` 充当真正的模型客户端，而是因为本次测试通过 `sql_generator` 注入确定性行为，不需要发起在线模型调用。这样测试重点落在：

- QueryAgent 的 guard 是否执行；
- schema 上下文是否能构建；
- 错误是否能进入修复路径；
- 最终结果和指标是否正确统计。

未来接入真实 LLM 时，可以把这个注入点换成真实异步模型适配器，同时保留 Runner 的结果模型和统计逻辑。

### 5.5 首轮运行和最终运行为什么分开

每个 case 至少运行两次逻辑：

```text
首轮运行：max_attempts = 1
    ↓
记录 first_pass_correct

最终运行：
    correction 开启 → max_attempts = 3
    correction 关闭 → max_attempts = 1
    ↓
记录 final_correct、recovered、attempts
```

伪代码如下：

```python
first_result = _run_case(
    case=case,
    max_attempts=1,
    few_shot_enabled=few_shot_enabled,
)

final_result = _run_case(
    case=case,
    max_attempts=3 if correction_enabled else 1,
    few_shot_enabled=few_shot_enabled,
)

first_pass_correct = first_result.matches_expected
final_correct = final_result.matches_expected
recovered = (not first_pass_correct) and final_correct
```

这样做比只运行最终流程更有信息量：如果最终正确率从 50% 提升到 83.3%，还需要知道提升的 33.3 个百分点中，有多少来自第一遍就正确，有多少来自纠错。

`max_attempts=3` 是一个 MVP 工程取舍：

- 允许首轮失败后有有限次数修复。
- 避免错误模型进入无限重试。
- 使延迟、token 和成本有上界。
- 更容易在面试中解释“可靠性和资源消耗的平衡”。

生产系统还可以进一步按照错误类型设置不同重试策略，但不能简单地无限 retry。

### 5.6 查询结果如何判断正确

不能只比较 SQL 字符串，因为不同 SQL 可能得到相同结果；也不能只判断 SQL 能否执行，因为“能执行”不等于“语义正确”。当前 Runner 采用下面的策略：

1. 执行 `expected_sql` 得到 oracle 的列名和行。
2. 执行 Agent 最终 SQL 得到实际的列名和行。
3. 对两者做可比较的规范化。
4. 比较规范化后的列序和行序。

核心规范化函数的逻辑如下：

```python
def _normalise_rows(columns: list[str], rows: list[tuple[object, ...]]) -> tuple:
    def normalise(value: object) -> object:
        if isinstance(value, float):
            return round(value, 6)
        if isinstance(value, list):
            return tuple(normalise(item) for item in value)
        if isinstance(value, dict):
            return tuple(sorted((key, normalise(item)) for key, item in value.items()))
        return value

    return (
        tuple(columns),
        tuple(tuple(normalise(value) for value in row) for row in rows),
    )
```

这里保留列顺序和行顺序，原因是当前 fixture 中的 oracle SQL 对结果顺序有明确预期。如果要支持“集合语义相等”，后续可以对无序结果做排序或多重集合比较，但必须根据查询是否含 `ORDER BY` 决定，不能一概而论。

浮点数保留 6 位小数是为了避免平均薪资等计算因为底层浮点表示造成无意义的差异。这个容差策略也要在文档中公开，否则别人无法判断“相等”是严格相等还是近似相等。

### 5.7 失败 case 的记录方式

每个 case 都会生成 `CaseMetrics`：

```python
class CaseMetrics(BaseModel):
    model_config = ConfigDict(extra="forbid")

    case_id: str
    first_pass_correct: bool
    final_correct: bool
    recovered: bool
    attempts: int = Field(ge=0, le=3)
    latency_ms: float = Field(ge=0)
    estimated_tokens: int = Field(ge=0)
    estimated_cost: float = Field(ge=0)
    status: Literal["completed", "failed"]
    error_kind: str | None = None
```

这比只输出一个总准确率更适合排查：

- 可以筛出所有 `final_correct=False` 的 case。
- 可以看哪些 `error_kind` 最难恢复。
- 可以判断失败来自首轮错误、权限拒绝、数据库执行错误还是结果比较失败。
- 可以分析高延迟是否集中在多次尝试的 case。

## 6. 指标定义、统计方法与消融实验

### 6.1 总体结果模型

```python
class BenchmarkResult(BaseModel):
    model_config = ConfigDict(extra="forbid")

    runner_version: str
    dataset: str
    dataset_size: int = Field(ge=1)
    model: str
    correction_enabled: bool
    few_shot_enabled: bool
    cost_per_1k_tokens: float = Field(ge=0)
    first_pass_accuracy: float = Field(ge=0, le=1)
    final_accuracy: float = Field(ge=0, le=1)
    recovery_rate: float = Field(ge=0, le=1)
    average_attempts: float = Field(ge=0)
    p50_latency_ms: float = Field(ge=0)
    p95_latency_ms: float = Field(ge=0)
    total_estimated_tokens: int = Field(ge=0)
    total_estimated_cost: float = Field(ge=0)
    cases: list[CaseMetrics]
```

把配置字段和指标放在同一个结果对象里很重要。否则拿到一份 `0.83` 的报告时，并不知道它是：

- 哪个数据集；
- 哪个模型；
- 是否开启纠错；
- 是否开启 few-shot；
- 使用了什么成本参数。

### 6.2 首轮准确率

定义为：

```text
first_pass_accuracy
    = 首轮结果正确的 case 数 / 总 case 数
```

它回答的是：

> 如果系统只允许模型生成并执行一次 SQL，不给它纠错机会，能答对多少？

这更接近模型和 schema 提示本身的直接能力。

### 6.3 最终准确率

定义为：

```text
final_accuracy
    = 最终结果正确的 case 数 / 总 case 数
```

它回答的是：

> 系统允许完整的 guard、执行、错误反馈和有限修复后，最终能答对多少？

最终准确率通常比首轮准确率高，但不应该只展示它，因为它隐藏了额外的延迟、token 和成本。

### 6.4 恢复率

当前实现的恢复率语义是：

```text
recovery_rate
    = 首轮错误但最终正确的 case 数 / 首轮错误的 case 数
```

例如：

- 总共 30 个 case；
- 首轮正确 20 个；
- 最终正确 25 个；
- 其中 5 个是从首轮错误恢复的；

那么：

```text
recovery_rate = 5 / (30 - 20) = 50%
```

当首轮没有任何失败时，分母为 0。实现中使用安全分母避免除零，但解释指标时应注明“没有可恢复样本”比简单写成 0% 更准确。当前合成数据通常包含故意失败样例，因此能够观察到恢复行为。

### 6.5 尝试次数

每个 case 的 `attempts` 表示 Agent 实际完成的 SQL 尝试次数，最多为 3。它可以用于分析：

- 平均多试了多少次；
- 最终正确是否依赖第三次尝试；
- 纠错收益是否值得额外成本。

一个简单的工程判断是同时看准确率和平均尝试次数，而不是只追求最终准确率。

### 6.6 P50 与 P95 延迟

平均延迟容易被少量极端值扭曲，因此 Runner 记录：

- P50：典型请求的中位数延迟。
- P95：95% 请求在该延迟以内完成，反映尾部延迟。

当前实现使用 nearest-rank 风格的百分位计算：

```python
def _percentile(values: list[float], percentile: float) -> float:
    ordered = sorted(values)
    rank = max(0, math.ceil(len(ordered) * percentile) - 1)
    return ordered[rank]
```

它不是所有统计库都采用的唯一定义，但它简单、稳定、适合当前小样本离线 benchmark。正式报告应该记录统计方法，避免不同实现对同一组数字产生不同结论。

### 6.7 token 和 cost 估算

离线 Runner 没有真实模型服务返回的 token usage，因此采用可解释的估算：

```text
estimated_tokens
    = schema.prompt_token_count × max(1, attempts)
      + ceil(query 字符数 / 4)

estimated_cost
    = estimated_tokens / 1000 × cost_per_1k_tokens
```

这里的 `cost_per_1k_tokens` 是 Runner 的参数，不是硬编码在每个 case 中。命令行可以通过 `--cost-per-1k-tokens` 修改。

必须明确它的局限性：

- `字符数 / 4` 只是粗略估算，不等同于具体 tokenizer。
- schema prompt 的 token 数来自本地估计，不包含所有 provider 的系统消息和工具消息细节。
- 没有真实 API 的 input/output token 分拆。
- 不能用该数字直接作为生产账单。

它在当前阶段的主要作用是对比配置：如果开启纠错后平均尝试次数上升，估算 token 和 cost 也应相应上升，至少可以做相对趋势分析。

### 6.8 消融实验

`run_ablation()` 固定同一个数据集，依次运行四种配置：

| 配置 | 纠错 | few-shot | 作用 |
|---|---:|---:|---|
| A | 开 | 开 | 完整方案 |
| B | 关 | 开 | 测试纠错收益 |
| C | 开 | 关 | 测试 few-shot 缺失时的纠错能力 |
| D | 关 | 关 | 基线方案 |

在当前 `eval_test` 的离线 fixture 上，得到过如下结果：

| 配置 | case 数 | final accuracy |
|---|---:|---:|
| 纠错开、few-shot 开 | 30 | 1.0000 |
| 纠错关、few-shot 开 | 30 | 0.8333 |
| 纠错开、few-shot 关 | 30 | 0.6667 |
| 纠错关、few-shot 关 | 30 | 0.5000 |

这个结果支持两个工程判断：

1. 纠错对故意注入的错误 SQL 有明显收益。
2. few-shot 对部分语义错误也有帮助。

但它不能证明在所有真实数据和所有模型上都一定保持同样提升。原因是当前 case 是受控合成数据，而且 SQL 选择是确定性的。面试中应该把这组数字称为“当前离线 fixture 上的消融结果”。

### 6.9 命令行入口

主要命令如下：

```bash
# 运行默认测试集
make eval

# 运行四组消融
make eval-ablation

# 直接运行指定数据集
uv run python -m eval.runner \
  --dataset eval_test \
  --correction on \
  --few-shot on \
  --output data/local/eval/eval_test.json
```

Runner 的参数包括：

- `--dataset`：`seed`、`eval_dev` 或 `eval_test`。
- `--correction`：`on` 或 `off`。
- `--few-shot`：`on` 或 `off`。
- `--ablation`：运行四组组合，而不是单个配置。
- `--output`：把结果写入 JSON 文件。
- `--cost-per-1k-tokens`：用于成本估算的价格参数。

## 7. 前端组件拆分与交互设计

### 7.1 为什么要拆组件

阶段四新增的需求来自三个不同的状态源：

1. QueryResult 的 `clarification`。
2. QueryResult 的 `steps` 和 `attempts`。
3. Task API 的事件流和最终 snapshot。

如果把三套状态都继续放在 `App.vue`，很容易出现：

- API 调用、事件解析、展示模板和样式混在一起；
- 任意一个状态字段变化都要阅读整个页面文件；
- SSE 的生命周期难以单独测试；
- 后续替换任务协议时会影响查询页面。

因此本阶段优先拆出三个低耦合组件。

### 7.2 `ClarificationPanel.vue`

组件的接口很小：

```ts
const props = defineProps<{
  clarification: QueryResult["clarification"]
}>()

const emit = defineEmits<{
  choose: [label: string]
}>()
```

它负责展示：

- Agent 的澄清问题；
- 澄清原因；
- 候选选项；
- 推荐选项。

用户点击选项时只发出 `choose(label)`，不直接修改父组件查询状态，也不直接调用 API。这样组件是一个纯展示/交互边界，父组件决定选择后如何重新查询。

设计上推荐选项可以使用视觉标记，但不能把推荐项强制当成用户选择。推荐是 Agent 的建议，最终决定仍然属于用户。

### 7.3 `ExecutionTimeline.vue`

这个组件展示两类信息：

```ts
defineProps<{
  steps: string[]
  attempts?: QueryResult["attempts"]
  status: string
}>()
```

`steps` 用于展示高层执行阶段，例如 schema、生成、验证、执行和报告；`attempts` 用于展开每次 SQL 尝试的细节：

- SQL 文本；
- 验证是否通过；
- 执行是否成功；
- `error_kind`；
- 数据库或校验错误信息。

把步骤和尝试分开很有必要：步骤适合普通用户理解，SQL 尝试适合开发者排查。前端可以默认折叠 SQL 细节，避免普通用户第一眼看到大量 SQL。

### 7.4 `DemoTaskPanel.vue` 的任务生命周期

组件实现的主要流程是：

```text
用户点击开始
    ↓
POST /api/tasks
    ↓
拿到 task_id
    ↓
创建 AbortController
    ↓
GET /api/tasks/{task_id}/events
    ↓
逐帧解析 SSE
    ↓
更新事件列表
    ↓
流结束后 GET /api/tasks/{task_id}
    ↓
展示 completed / failed / cancelled snapshot
```

演示任务使用固定文本和 session：

```ts
const task = await api.createTask(
  "阶段四离线演示任务",
  "stage4-demo",
)
```

这不是让用户输入真实爬虫任务，而是让面试演示可以在本地稳定启动，并展示任务事件模型。

组件还做了两个重要的生命周期处理：

1. 使用 `AbortController` 取消正在进行的 fetch 流。
2. 组件卸载时 abort，避免离开页面后仍然更新已经销毁的组件。

如果流读取失败，组件会把错误转换为一条可见的失败事件，而不是静默吞掉异常。这符合项目的错误处理原则：用户至少能看到“事件流失败”，而不是界面永久停留在 loading。

### 7.5 `App.vue` 的组合方式

`App.vue` 现在负责把新增组件放回查询工作区：

- 澄清结果存在时显示 `ClarificationPanel`。
- 查询有执行过程时显示 `ExecutionTimeline`。
- 右侧任务区域显示 `DemoTaskPanel`。
- 已有的结果表格、分析图和 Markdown 报告继续复用。

这种组合方式可以避免为了阶段四而破坏阶段三已有的结果展示。阶段四的前端重点是“增加可观测性和演示入口”，不是把已有 UI 全部推倒重写。

## 8. SSE 任务流与状态展示

### 8.1 为什么使用 SSE

阶段四需要展示后台任务的执行轨迹。与轮询相比，SSE 的优势是：

- 服务端可以主动推送事件；
- 浏览器原生支持文本事件流语义；
- 单向服务端到客户端更新适合任务进度；
- 比 WebSocket 更轻量，不需要双向消息协议。

任务状态主要是后端推动前端更新，所以 SSE 在当前 MVP 中是合适的选择。若未来需要客户端实时取消、暂停、修改任务，仍然可以用普通 REST 控制接口配合 SSE，而不一定马上升级成 WebSocket。

### 8.2 事件和快照的区别

任务 API 同时提供事件流和最终状态快照：

| 类型 | 作用 | 适合场景 |
|---|---|---|
| Event | 描述状态变化，例如某一步开始或完成 | 时间线、实时进度、审计 |
| Snapshot | 描述当前任务完整状态 | 刷新页面、流结束后恢复状态、失败兜底 |

事件是增量信息，快照是当前状态。只依赖事件时，浏览器刷新后很难恢复完整界面；只依赖快照时，又无法展示中间过程。两者结合可以兼顾可观测性和恢复能力。

### 8.3 `TaskEvent` 和 `TaskSnapshot` 类型

前端新增类型如下：

```ts
export interface TaskEvent {
  event_id: string
  task_id: string
  sequence: number
  event_type: string
  timestamp: string
  payload: Record<string, string | number | boolean | null>
}

export interface TaskSnapshot {
  task_id: string
  status:
    | "created"
    | "running"
    | "waiting_clarification"
    | "completed"
    | "failed"
    | "cancelled"
  sequence: number
  session_id: string
  result?: {
    summary: string
    steps: string[]
    data: Record<string, unknown>
  } | null
  error?: {
    code: string
    message: string
    detail?: string | null
  } | null
}
```

这里没有把 payload 直接写成 `any`，而是限制为可序列化的基础值。任务结果中的 `data` 仍然使用 `Record<string, unknown>`，因为它是面向业务结果的扩展载荷；如果后续要进入核心计算逻辑，应进一步建模。

### 8.4 SSE 的帧格式

SSE 事件通常由空行分隔，一个事件可能包含：

```text
event: task.started
id: 2
data: {"event_id":"...","sequence":2,...}

```

`api.ts` 的 `streamTaskEvents()` 使用 `fetch`、`ReadableStreamDefaultReader` 和 `TextDecoder` 逐步读取响应，维护一个字符串 buffer：

```ts
const reader = response.body?.getReader()
const decoder = new TextDecoder()
let buffer = ""

while (reader) {
  const { value, done } = await reader.read()
  if (done) break

  buffer += decoder.decode(value, { stream: true })
  const frames = buffer.split("\n\n")
  buffer = frames.pop() ?? ""

  for (const frame of frames) {
    const data = parseSseFrame(frame)
    if (!data) continue
    onEvent(JSON.parse(data) as TaskEvent)
  }
}
```

实际实现还会处理 `event`、`id` 和多行 `data` 字段，并在流结束后请求 task snapshot。关键点是不能假设一次 `reader.read()` 就正好得到完整事件：网络 chunk 可能截断在 JSON 中间，所以必须 buffer 到空行边界再解析。

### 8.5 事件顺序和状态机

一个正常任务可以产生类似顺序：

```text
task.created
    ↓
task.started
    ↓
step.started
    ↓
heartbeat（可选）
    ↓
step.completed
    ↓
task.completed
```

异常路径可能是：

```text
task.created → task.started → task.failed
task.created → task.cancelled
```

`sequence` 用于排序、去重和断点恢复。客户端不应只依赖事件到达顺序，因为未来可能存在重连或不同传输实现；应该优先使用 sequence。

后端的事件存储采用追加式 JSONL 思路，并为 task 提供 snapshot。SSE 端点可以根据 `Last-Event-ID` 或对应序号返回断点之后的事件。当前前端演示已经能够读取和显示一次完整事件流，但自动重连策略仍可进一步增强。

### 8.6 同步查询与异步任务的边界

这是阶段四实现中需要特别讲清楚的一点：

- 现有 QueryPanel 的自然语言查询仍然通过已有查询 API 获取 `QueryResult`。
- `ExecutionTimeline` 直接展示 QueryResult 中的 `steps` 和 `attempts`。
- `DemoTaskPanel` 通过任务 API 和 SSE 展示一个可复现的后台任务生命周期。

也就是说，本阶段已经完成了“查询结果的执行轨迹”和“任务 API 的 SSE 演示”，但没有隐瞒成“每一次查询都已经完全异步化并通过 SSE 返回”。

如果继续生产化，可以把 QueryAgent 的执行过程接入 TaskRuntime：

```text
POST /api/tasks（包含自然语言问题）
    ↓
TaskRuntime 创建任务
    ↓
QueryAgent 每个阶段 emit event
    ↓
SSE 推送 task / step / attempt 事件
    ↓
完成时 snapshot.result = QueryResult
```

这样 `DemoTaskPanel` 的协议可以逐步变成真正的查询工作流协议。

## 10. 测试、验证结果与结果边界

### 10.1 自动化测试

阶段四新增测试覆盖：

1. 三路数据集展开后的数量必须是 `seed=6`、`eval_dev=20`、`eval_test=30`。
2. seed benchmark 的最终准确率为 1，首轮准确率低于最终准确率，并且能够观察到恢复。
3. P50、P95 和 token 估算均为正数。
4. 消融实验必须包含四组配置，并且完整配置的最终准确率高于关闭全部增强的基线。

当前仓库验证结果：

```text
全量后端测试：224 passed, 1 warning
阶段四测试：3 passed
前端构建：vue-tsc + vite 通过
数据集数量：seed=6, eval_dev=20, eval_test=30
```

其中唯一 warning 是现有依赖栈中的 Starlette deprecation warning，不影响阶段四测试结果。

### 10.2 seed benchmark 示例结果

一次 seed 运行得到过以下结果：

| 指标 | 值 |
|---|---:|
| dataset size | 6 |
| first pass accuracy | 0.6667 |
| final accuracy | 1.0000 |
| recovery rate | 1.0000 |
| average attempts | 1.3333 |
| P50 latency | 约 7.7 ms |
| P95 latency | 约 14.0 ms |
| estimated tokens | 14980 |
| estimated cost | 0.01498（按当前参数） |

这些数字适合用来验证 Runner 是否工作，但不应被解读为线上 LLM 的真实延迟或费用。尤其是本地 DuckDB 和确定性 SQL 生成器的延迟，和远程模型调用延迟不是同一个量级。

### 10.3 为什么测试结果不能过度解读

当前 benchmark 的优点是稳定、可复现、便于快速迭代；局限也很明确：

- case 数量虽然达到阶段目标，但仍然远小于真实用户分布。
- 数据来自固定 jobs fixture，schema 和数据分布都比较稳定。
- SQL 生成器是确定性的，不会模拟真实模型的语言理解波动。
- token 和 cost 是估算值。
- 延迟主要反映本地执行，不含真实网络和 provider 排队。

因此合适的表述是：

> 在当前离线合成 fixture 和确定性评测配置下，完整方案的 final accuracy 为 100%，并且相对关闭纠错与 few-shot 的基线有明显提升；该结果用于验证工程链路和相对收益，不等同于真实生产流量上的模型泛化指标。

### 10.4 环境边界

在某些受限环境中，`uv run` 可能因为 uv cache 目录权限而失败，但如果项目的 `.venv` 已经存在，可以直接使用 `.venv/bin/python -m pytest` 完成测试，前端仍然可以使用 `npm --prefix frontend run build` 验证。

面试或交付时应优先记录真正的命令和失败原因，不要把环境权限问题误报为代码测试失败。

## 11. 关键函数与参数速查

### 11.1 评测模型

| 对象 | 关键参数 | 说明 |
|---|---|---|
| `EvalCase` | `case_id` | 稳定定位一个测试样本 |
| `EvalCase` | `query` | 自然语言输入 |
| `EvalCase` | `expected_sql` | 生成 oracle 结果 |
| `EvalCase` | `first_sql` | 首轮候选 SQL |
| `EvalCase` | `repair_sql` | 修复阶段候选 SQL |
| `EvalCase` | `few_shot_sql` | few-shot 开启时的候选 SQL |
| `EvalCase` | `repeat` | 数据模板展开次数 |
| `CaseMetrics` | `attempts` | 实际尝试次数，上限为 3 |
| `CaseMetrics` | `recovered` | 是否从首轮错误恢复 |
| `BenchmarkResult` | `correction_enabled` | 是否允许多次尝试 |
| `BenchmarkResult` | `few_shot_enabled` | 是否启用 few-shot 路径 |
| `BenchmarkResult` | `cost_per_1k_tokens` | 成本估算参数 |

### 11.2 数据集函数

#### `load_dataset(name, root=DATA_ROOT)`

- `name`：只能是 `seed`、`eval_dev` 或 `eval_test`。
- `root`：便于测试时注入临时数据目录。
- 返回值：经过校验和展开的 `EvalDataset`。
- 失败情况：文件不存在、JSON 无效、字段不合法、ID 重复、dev/test 数量不足。

#### `load_all_datasets(root=DATA_ROOT)`

- 一次加载三路数据。
- 检查跨数据集 ID 冲突。
- 检查 dev 与 test 合计至少 50 个 case。
- 适合被 CI 或阶段四测试调用。

### 11.3 Runner 函数

#### `_prepare_database(root)`

- `root`：当前 benchmark 的临时根目录。
- 返回：构建好的数据库根目录。
- 副作用：在临时目录生成 raw 数据和数据库文件。
- 设计目的：每次从固定 fixture 隔离重建。

#### `_make_agent(database_root, case, max_attempts, few_shot_enabled)`

- `database_root`：数据库位置。
- `case`：当前评测样本。
- `max_attempts`：最多执行几轮 SQL；首轮为 1，纠错流程为 3。
- `few_shot_enabled`：决定是否选用 `few_shot_sql`。
- 返回：复用生产 Agent 结构但注入确定性生成函数的 `QueryAgent`。

#### `run_benchmark(dataset, correction_enabled=True, few_shot_enabled=True, model_name="deterministic-eval", cost_per_1k_tokens=0.001)`

- `dataset`：`EvalDataset`。
- `correction_enabled`：控制是否允许多次尝试。
- `few_shot_enabled`：控制 few-shot 候选是否生效。
- `model_name`：写入报告，用于区分实验配置；当前默认是确定性评测名。
- `cost_per_1k_tokens`：成本估算参数。
- 返回：完整的 `BenchmarkResult`。

#### `run_ablation(dataset, ...)`

- 自动运行四组纠错/few-shot 组合。
- 返回带配置标签的结果列表。
- 适合生成对比报告，而不是只看一份完整方案结果。

### 11.4 前端函数

#### `api.createTask(text, sessionId)`

- `text`：任务描述。
- `sessionId`：任务所属会话。
- 返回：包含 `task_id` 的任务创建响应。

#### `api.streamTaskEvents(taskId, onEvent, signal?)`

- `taskId`：要监听的任务。
- `onEvent`：每解析出一个 `TaskEvent` 时回调。
- `signal`：可选 AbortSignal，用于取消流。
- 关键职责：检查响应、读取 chunk、处理 buffer、按空行切帧、解析 JSON、读取最终 snapshot。

#### `DemoTaskPanel.startDemo()`

- 创建固定离线演示任务。
- 清空旧事件和错误状态。
- 建立 AbortController。
- 调用 SSE API 并把事件追加到列表。
- 组件卸载时终止连接。

## 12. 异常场景、工程取舍与后续改进

### 12.1 数据集错误

当前处理策略：

- JSON 语法错误：立即失败并指出数据文件/行。
- Pydantic 校验失败：拒绝非法字段、空字符串、超长字符串和非法 repeat。
- 重复 ID：立即失败，避免结果覆盖。
- dev/test 数量不足：立即失败，避免生成看似正式的低样本报告。

后续可进一步增加：

- 数据集 schema 版本号。
- 自动输出失败行附近的上下文。
- 在 CI 中校验 expected SQL 必须可执行。

### 12.2 SQL 失败和纠错上限

当前纠错最多 3 次，避免无限循环。但还可以进一步区分：

- 语法错误：通常可进入修复。
- 未知列：可以携带 schema 错误进入修复。
- 权限拒绝：不应通过无限重试绕过安全边界。
- 结果为空：不一定是 SQL 错误，可能是用户条件本来没有匹配数据。
- 超时：应考虑取消和资源限制，而不是无脑重试。

真正生产化时，重试条件应是错误类型的白名单，并且要记录每次 retry 的原因。

### 12.3 结果等价性的改进

当前比较列顺序和行顺序，适合现有 fixture，但不覆盖所有 SQL 语义等价情况。未来可以：

- 对明确无序的结果使用集合/多重集合比较。
- 统一日期、Decimal、NULL 和时区表示。
- 对浮点数采用按绝对误差和相对误差的比较。
- 同时记录 SQL 字符串、执行计划和结果 fingerprint。
- 增加人工审核的困难 case。

### 12.4 真实模型评测

后续接入真实模型时，应增加：

- 可插拔的异步 ModelClient。
- 真实 input/output token usage。
- provider、model、temperature、prompt version、schema version。
- 重试和限流记录。
- 随机种子或多次重复运行。
- 置信区间和显著性分析。

当前 `model_name` 已经写入 `BenchmarkResult`，为以后按模型对比保留了入口，但不能因为字段存在就声称已经完成真实模型实验。

### 12.5 SSE 的后续增强

当前前端一次性读取 SSE 并在流结束后读取 snapshot，后续可以增强：

- 自动重连。
- 保存最后一个 `sequence` 并发送 `Last-Event-ID`。
- 重连后去重。
- 长时间无事件时显示 heartbeat 超时提示。
- 对非法 JSON 事件进行协议级错误提示。
- 任务取消按钮调用 REST cancel endpoint。
- 对 `waiting_clarification` 状态增加真实交互。

### 12.6 前端的后续拆分

当前优先拆出了阶段四新增的三个组件，但 `App.vue` 仍然保留较多历史工作区组合逻辑。后续可以继续抽离：

- 查询输入区。
- 历史记录列表。
- 结果展示区。
- 会话上下文栏。
- Task 状态 store。

不应该为了追求文件行数立刻大规模重构；更合理的策略是按状态边界和可测试性逐步拆分。

### 12.7 CI 和发布

阶段四之后可以把以下内容接入 CI：

```text
提交代码
  ↓
pytest 全量
  ↓
阶段四 eval smoke
  ↓
eval_test 指标回归阈值
  ↓
前端 typecheck/build
  ↓
生成评测 artifact
```

回归阈值可以包括：

- final accuracy 不低于历史基线。
- recovery rate 不显著下降。
- P95 不超过预算。
- 类型检查和构建必须通过。

不过阈值也必须考虑数据集和模型版本，否则一旦更新 prompt 或 fixture，CI 只会给出难以解释的失败。

## 13. 模拟求职面试问答

下面的问题按“常见主问题—追问—推荐回答”的形式整理。回答时建议先给结论，再补实现细节和边界。

### Q1：为什么还要做阶段四？前面 Agent 已经能运行了，不是已经完成了吗？

**推荐回答：**

前面的阶段主要解决“功能能不能跑通”，阶段四解决“效果能不能被证明、过程能不能被解释、项目能不能被复现”。如果只有手工 demo，我无法回答首轮准确率、纠错收益、P95 延迟和成本。阶段四用固定数据集和统一 Runner 建立了可重复的证据，同时把澄清、执行轨迹和后台任务状态接入前端，最后用 Makefile 和离线 fixture 降低演示对网络、登录和实时爬虫的依赖。

**可能追问：** 阶段四最重要的是评测还是前端？

两者都重要，但优先级上评测是可信度基础，前端是可观测性和演示入口。没有评测，页面只能展示成功案例；没有前端观测，评测数字又很难让面试官直观看到 Agent 如何工作。

### Q2：为什么要把数据分成 seed、dev、test 三份？

**推荐回答：**

seed 用于快速 smoke test 和本地演示，dev 用于开发过程中调试指标和修复逻辑，test 用于稳定的离线报告。分离可以避免把已经看过、反复调过的样例和最终报告混在一起。当前项目的 test 仍然是合成 fixture，因此我会把它称为离线 benchmark，而不会声称它代表真实生产分布。

### Q3：你的 50 多个 case 是怎么来的？会不会存在数据泄漏？

**推荐回答：**

当前共有 6 个 seed、20 个 dev 和 30 个 test，部分模板通过 `repeat` 展开成稳定 ID。每个 case 同时记录自然语言问题、expected SQL、首轮 SQL、修复 SQL 和可选 few-shot SQL，主要用于离线验证评测框架和纠错分支。它不是严格意义上的大规模模型泛化测试，确实存在受控 fixture 和模板相似的问题，所以我在 README 和面试中明确披露这一点。下一步会增加按意图、schema 变化和数据分布隔离的隐藏测试集，并避免 prompt 设计直接使用 test case。

### Q4：为什么不直接比较生成的 SQL 字符串？

**推荐回答：**

SQL 字符串不唯一，不同写法可能返回相同结果；反过来，SQL 能执行也不代表语义正确。因此当前实现执行 expected SQL 和实际 SQL，然后比较规范化后的列和行。后续可以根据查询是否有 `ORDER BY` 采用有序或无序比较，并进一步统一 NULL、Decimal、日期和浮点误差。

### Q5：首轮准确率、最终准确率和恢复率分别说明什么？

**推荐回答：**

首轮准确率衡量只给模型一次机会时的能力；最终准确率衡量完整 guard、执行和有限纠错后的能力；恢复率衡量首轮失败样本中有多少被系统救回来。这样可以把模型直接能力和工程纠错能力拆开。如果只看最终准确率，就不知道提升到底来自模型本身还是 retry/repair。

### Q6：恢复率的分母为什么不是总 case 数？

**推荐回答：**

因为恢复率要回答的是“已经失败的样本中，有多少被恢复”，所以分母是首轮失败数。如果首轮没有失败，恢复率在语义上是“不适用”，而不是简单代表系统恢复能力为 0。实现上会避免除零，报告解释时会注明这一点。

### Q7：为什么最多尝试 3 次？为什么不一直重试直到成功？

**推荐回答：**

无限重试会造成延迟、token、成本和数据库资源不可控，也可能重复触发同一种错误。当前 3 次是 MVP 的资源上界：首轮加两次修复机会，足够覆盖典型 schema 或语法错误，同时让 P95 和成本可测。生产化时会按错误类型设置可重试白名单，权限拒绝等安全错误不会无限重试。

### Q8：如何证明纠错和 few-shot 真的有用？

**推荐回答：**

我使用四组消融：纠错开/few-shot 开、纠错关/few-shot 开、纠错开/few-shot 关、两者都关。保持数据集和其他配置一致，只改变一个因素，就可以观察相对变化。当前离线 test fixture 上完整方案为 1.0，关闭纠错为约 0.8333，关闭 few-shot 为约 0.6667，全部关闭为 0.5。这个结论只适用于当前合成 benchmark，不能直接外推到线上模型。

### Q9：你为什么在评测中不调用真实 LLM？

**推荐回答：**

因为阶段四首先要验证评测框架本身，而真实 LLM 会带来网络、费用、限流和随机性。如果 Runner 直接依赖模型，一旦结果异常，很难判断是模型波动还是指标代码有 bug。因此当前用确定性 SQL 生成器注入 QueryAgent，测试 guard、执行、修复、统计和报告链路。真实 LLM 是下一层实验，会使用同样的结果模型和可插拔客户端接入。

### Q10：那你的准确率是不是没有意义？

**推荐回答：**

它有明确但有限的意义：可以证明当前离线 fixture、Agent 流程和评测 Runner 的行为是可重复的，也能比较纠错和 few-shot 的相对影响。但它不能说明真实大模型在未知数据上的泛化能力。因此我会同时报告数据集、模型模式、fixture 来源和指标边界，而不会只报一个漂亮的 100%。

### Q11：为什么要记录 P50 和 P95，而不是只记录平均延迟？

**推荐回答：**

平均值容易被少数慢请求掩盖。P50 代表典型用户体验，P95 反映尾部请求，尤其能看到多次 SQL 修复或复杂查询带来的长尾。Agent 系统不能只追求平均成功率，还要控制用户在最慢一部分请求上的等待时间。

### Q12：你的 token 和 cost 是真实的吗？

**推荐回答：**

当前不是 provider 账单，而是可解释的估算：schema prompt 的 token 估计乘以尝试次数，再加上自然语言问题的粗略 token 估计，最后乘以可配置的每千 token 价格。它适合做不同配置之间的相对比较。接入真实模型后，应使用 provider 返回的 input/output token usage，并按模型、版本和价格表记录真实成本。

### Q13：为什么每个 benchmark 都重新做 ETL？这样不是很慢吗？

**推荐回答：**

这是隔离和可重复性的取舍。每次从同一个 fixture 创建临时数据库，可以避免旧数据、测试顺序和缓存污染结果，并且支持不同配置隔离运行。对当前几十个本地 case，ETL 成本可接受。数据规模增大后，可以使用只读数据库快照或预构建 artifact，但仍应保证每个实验看到的输入版本固定。

### Q14：评测 Runner 为什么还要使用 AccessScope？

**推荐回答：**

如果评测绕过权限，测到的只是“裸 DuckDB 能不能执行 SQL”，不能证明实际 Agent 在安全边界内可用。Runner 使用和业务路径一致的 jobs_market 数据库和表白名单，确保 schema、guard 和执行都经过相同的访问约束。评测代码也不能因为属于测试就默认拥有全库权限。

### Q15：为什么前端要拆成三个组件？

**推荐回答：**

这三个组件对应三个不同的状态和职责：澄清面板负责用户选择，执行时间线负责 QueryResult 的步骤和 SQL 尝试，DemoTaskPanel 负责任务创建、SSE 生命周期和最终 snapshot。把它们拆开可以减少 App.vue 的状态耦合，也方便分别测试和替换协议。当前采用渐进式拆分，保留已有表格、图表和 Markdown 逻辑，控制改动风险。

### Q16：为什么使用 SSE，不使用 WebSocket？

**推荐回答：**

当前任务状态主要是服务端单向推送，SSE 更简单，浏览器和 HTTP 基础设施支持也更直接。任务取消仍然可以通过 REST 接口完成，不需要为了一个单向进度流引入双向协议。只有当产品需要高频双向控制、协作或实时交互时，我才会评估 WebSocket。

### Q17：SSE 的代码如何处理网络 chunk 被截断的问题？

**推荐回答：**

不能假设一次 `reader.read()` 正好返回一个完整事件。我使用 `TextDecoder` 把 chunk 解码后追加到 buffer，按 SSE 空行分割出完整 frame，把最后一个不完整片段留在 buffer 中，下一次继续拼接。完整 frame 再解析 `event`、`id` 和 `data`，最后对 data 做 JSON 校验。这样 JSON 被截断在中间时不会立即解析失败。

### Q18：如果 SSE 中途断开，当前系统如何处理？

**推荐回答：**

当前前端会捕获流错误并展示失败事件，同时在正常结束后读取 snapshot。后端协议已经有 sequence/事件 ID 和 snapshot，为自动恢复保留了基础。下一步会保存最后一个 sequence，通过 `Last-Event-ID` 重连、去重并继续展示；如果 snapshot 已经是终态，则直接以 snapshot 为准。

### Q19：事件流和最终 snapshot 为什么要同时存在？

**推荐回答：**

事件适合展示过程和审计，snapshot 适合刷新页面、断线恢复和获取当前完整状态。只用事件，刷新后要重放全部历史；只用 snapshot，又看不到中间步骤。两者组合可以同时满足实时观测和最终一致的状态恢复。

### Q20：当前查询是否已经完全异步化？

**推荐回答：**

阶段四当前明确分成两条路径：QueryResult 通过已有查询 API 返回，并由 ExecutionTimeline 展示 SQL 尝试；DemoTaskPanel 通过 Task API 和 SSE 展示后台任务事件。因此 SSE 任务协议已经可以演示，但现有查询还没有全部改成后台异步任务。后续可以让 QueryAgent 的每个阶段向 TaskRuntime emit event，并在 snapshot.result 中返回 QueryResult，从而把两条路径合并。

这个回答比直接声称“已经完成异步查询”更准确，也体现了对系统边界的理解。

### Q21：为什么演示不依赖实时爬取和登录？

**推荐回答：**

面试演示的目标是证明 Agent、评测和 UI 链路，而不是证明某个网站当前可爬。实时爬取会受到网络、验证码、登录过期、页面变化和第三方服务限制影响。使用脱敏/合成 fixture 和本地 ETL，别人可以稳定复现，也不会引入隐私和授权风险。生产环境仍可把采集作为独立上游系统接入。

### Q22：你的测试覆盖了什么？

**推荐回答：**

全量后端测试有 224 个通过，阶段四新增 3 个测试，分别覆盖数据集数量、seed benchmark 的首轮/最终/恢复指标，以及四组消融配置。前端通过 vue-tsc 和 Vite build。阶段四测试不是只测页面快照，而是同时验证输入数据契约、评测结果方向和构建产物。

### Q23：如果让你继续做，你会优先改什么？

**推荐回答：**

我会按风险优先级做三件事：第一，接入真实异步模型客户端并记录真实 token usage；第二，把 QueryAgent 执行阶段接入 TaskRuntime，实现查询本身的 SSE 进度和可恢复；第三，扩展隐藏 test 集，加入不同 schema、空结果、权限拒绝、日期边界和同义问法，并为准确率和 P95 增加回归阈值。这样可以把当前“可复现 MVP”逐步推进到更接近生产的评测系统。

### Q24：这个阶段最能体现你的工程能力的地方是什么？

**推荐回答：**

我认为不是某一段 UI，而是把正确性、可靠性和可交付性同时纳入设计：输入数据用严格模型校验，评测使用隔离数据库和统一 oracle，纠错收益通过消融拆分，成本和延迟有记录，前端能展示澄清和执行过程，最后还能用离线 fixture 和 Makefile 复现。它体现了我不会只追求 demo 成功，还会考虑如何测量、解释和交付。
